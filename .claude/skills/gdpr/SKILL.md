## Чеклист «новая фича → обязательства» (прогоняй в каждом PR с данными)

- **Новое поле/таблица/кеш-ключ с данными пользователя?**
  - Минимизация (ст. 5(1)(c)): зачем; можно ли меньше/короче/хешем/без?
    Образцы в репо: `ip_hash` вместо IP, `country` вместо гео-точки,
    `session_token` — случайный UUID, `visitors.referrer` обрезан до 300.
  - Ретеншен (ст. 5(1)(e)): «бессрочно» — не дефолт, а решение. Окна
    исполняет ежедневный крон `lib/retention.ts` (#162): политика = таблица +
    индексированная колонка + срок + цитата из `/privacy` §6, тест
    пришпиливает список. Новая таблица с персональными данными либо
    добавляет туда политику (и срок в `/privacy`, если его там нет — это
    текст политики, решает владелец), либо объясняет в колонке «Ретеншен»
    карты, почему живёт с аккаунтом.
  - Стирание: FK на `users.id` с `onDelete: "cascade"` (образец —
    `watch_progress`), либо `set null` с обоснованием, почему строка должна
    пережить аккаунт псевдонимной (образец — `visitors`). Таблица без FK на
    `users`, но с персональными полями (как `show_reminders.email`) обязана
    ответить в карте, чем она стирается.
  - Экспорт: попадёт ли в выгрузку по ст. 15/20 (#163)? Персональное — да.
  - Карта: строка в `references/data-map.md` ТЕМ ЖЕ PR.
- **Новый внешний сервис/SDK/эндпойнт, куда уходят данные?** → это
  процессор (ст. 28): DPA до прод-данных, механизм трансфера (DPF/SCC),
  строка в `references/processors.md` + `docs/registry.md` (пока DPA не
  подтверждён). Новый вид данных наружу — сперва слово владельца. Пуши для
  приложения (#98) — процессор Expo/FCM/APNs появляется в таблице ДО того,
  как уйдёт первый пуш.
- **Меняешь письма/пуши/события аналитики?** Их содержимое видят провайдеры
  (Resend видит адрес + тему + тело; PostHog — свойства событий и `email`
  персоны; пиксели — id событий). В письма — только контент шоу (название,
  эпизод, логлайн, кадр), никаких данных пользователя кроме адреса; в
  свойства событий — id, слаги, номера, режимы, но не email/имена/тексты
  (`lib/posthog-events.ts`, `lib/openai-pixel-events.ts`). Обнови абзац «Что
  уходит во внешние сервисы» в карте.
- **LLM-промпты?** Сегодня их нет. Первый LLM-вызов над данными
  пользователей = решение владельца, новый процессор, абзац «Что уходит в
  LLM» в карте. Отправлять минимум (email/id — нет), в пределах лимитов
  конфига.
- **Логи/трекер ошибок/аналитика** — правило CLAUDE.md: данные
  пользователей НИКОГДА; только id, статусы, длительности. Новый серверный
  путь, который логирует, получает кейс в `lib/log-audit.test.ts` ТЕМ ЖЕ PR.
  Sentry: скрабберы в `lib/observability.ts` — новое поле в payload
  ошибок = кейс в их сьюте.
- **Медиа/файлы?** Пользователи сегодня ничего не загружают (Blob хранит
  только артворк шоу и аватары виртуальных актёров). Появится аватар/загрузка
  пользователя → EXIF-стрип на пайплайне, путь в Blob привязан к `users.id`,
  удаление объекта — явный шаг каскада (Blob не знает о наших FK).
- **Черновики/джобы/кеши с контентом?** Наследуют чувствительность
  оригинала: тот же запрет на логи, ретеншен, каскад. Сегодня кешей с
  персональными данными нет (`roleCache` в `proxy.ts` — 5 с, только роль).
- **Инструменты разработки с доступом к проду.** `.env.local` и Neon MCP
  смотрят в боевую базу. Персональные колонки (`email`, `referrer`,

  счётчики, агрегаты. Вопрос «а какие адреса подписались» решается
  `count(*)`, не `select email`.

## Канон стирания (ст. 17) — как это устроено по факту

Факт на 15.09.2026 (полная таблица — `references/data-map.md`):

- **Триггер** — удаление аккаунта в Clerk (UserProfile → «Delete account»,
  дашборд, или наш ручной запрос). Вебхук `user.deleted`
  (`app/api/webhooks/clerk/route.ts`, с #161) зовёт единственную механику —
  `lib/erase-user.ts:eraseUser` (с #180 её же руками запускает
  `pnpm erase-user <clerk id> --apply`: вебхук не дошёл или restore вернул
  строки; dry-run по умолчанию, `DATABASE_URL` явно, `.env.local` не
  читается): `DELETE FROM users WHERE id = <clerk id>` → каскады FK + явное
  удаление `show_reminders` по адресу аккаунта + явное удаление
  `idea_submissions` по адресу аккаунта (#297; только адрес, lowercase —
  `user_id` у таблицы нет; шаг идёт ДО `DELETE FROM users`, пока адрес
  читается). Идемпотентно: повтор для уже
  стёртого — 200 без записи. Ручной GDPR-запрос исполняется удалением в
  Clerk тем же путём, не отдельным SQL — скрипт повторяет эффект, не
  заменяет триггер (ранбук §4). Ops-условие: прод-эндпойнт в дашборде Clerk
  должен быть подписан на `user.deleted` (пока нет — строка в
  `docs/registry.md`).
  Самообслуживание в приложении (#309, 27.09) от этого условия не зависит:
  «Delete account» во вкладке «Аккаунт» → `POST /api/v1/account/delete`
  (только Bearer — сессия из cookie получает 401) зовёт `eraseUser` сам и
  лишь ПОТОМ удаляет аккаунт в Clerk (`users.deleteUser`, 404 = уже удалён).
  Порядок обратный вебхуку намеренно: сбой стирания оставляет живую сессию,
  и повтор из приложения сходится; удалённый первым аккаунт в Clerk повтора
  не дал бы. Цена порядка — окно, в котором heal `/v1/progress` (#303)
  может вернуть строку `users` из ещё живого Clerk; поэтому после ответа
  Clerk — и при не-404 сбое тоже: таймаут не доказывает, что аккаунт жив, —
  маршрут смотрит в `users` ещё раз и стирает найденное. Пришедший
  позже вебхук находит строку стёртой — `not_found`, 200 без записи.
  Поздняя доставка `user.created` (Svix повторяет часами) строку не
  воскрешает: вебхук перед вставкой спрашивает Clerk `users.getUser(<id>)`,
  404 → ничего не пишет, лог по id, 200; иная ошибка Clerk → 500 (#336).
  Ответ маршрута, потерянный по дороге (таймаут 45 с, обрыв, повтор с 401),
  приложение не выдаёт за «не удалось»: после любого сбоя оно спрашивает
  Clerk о сессии (`getToken({ skipCache: true })`) — её нет → выход и
  главная, как при успехе; жива или Clerk молчит → честная ошибка (#336).
  Остаточные дыры этого пути — #336. Страницы удаления на вебе нет (`docs/registry.md`).
  Аккаунт с входом через Apple (#407): приложение перед запросом берёт у
  листа Apple свежий authorization code, маршрут ПОСЛЕ стирания и ДО Clerk
  меняет его на токены и отзывает грант (`lib/apple-revoke.ts`, best-effort,
  без кода / без `APPLE_*` в env — типизированный пропуск; в лог — только
  статус). Остальные пути кода Apple не имеют и грант не отзывают.
  Четвёртый вход в тот же `eraseUser` — конфликт адреса (#380,
  `lib/user-mirror.ts`): строка `users` под ДРУГИМ Clerk id держит адрес
  нового аккаунта — остаток удаления в Clerk без стирания (#172). Запись
  зеркала (одна функция для `user.created` и `getOrSyncCurrentUser`)
  спрашивает Clerk об этом id: 404 → `eraseUser(<тот id>)` и повтор
  вставки; аккаунт жив с другим адресом → строке пишется его текущий адрес
  (`user.updated` не зеркалится — `docs/registry.md`); жив и адрес его или
  ошибка Clerk → ничего не стирается, лог + Sentry по id. Такое стирание
  ПОЗДНЕЕ — адрес уже принадлежит новому аккаунту (скорее всего тому же
  человеку), поэтому `eraseUser` получает `addressReassignedAt` = момент
  создания нового аккаунта: поиска клиентов Stripe по адресу нет (иначе он
  навечно затумбстоунил бы клиента, которого создал гостевой checkout НОВОГО
  аккаунта, — «оплачено, аккаунта нет»), `show_reminders` / `idea_submissions`
  по адресу — только созданные раньше нового аккаунта; всё по старому id
  (отмена подписки, тумбстоун `stripe_customer_id`, каскады, PostHog) — как
  обычно. Остаток окна «удалён → зарегистрировался заново» — `docs/registry.md`.

  `users`: новая таблица со ссылкой на `users` без `onDelete` ломает тест —

  реестра заявок (`db-restore.md` §7) или тем же скриптом, если адрес под

- **Каскады FK от `users.id`** (`db/schema/*`, проверено по коду):
  `CASCADE` — `subscriptions`, `watch_progress`, `watch_days`; `SET NULL` —
  `trial_sessions.user_id`, `visitors.user_id` (история визитов остаётся
  псевдонимной: aid, referrer, utm, country), `show_reminders.user_id` — но на
  этот SET NULL обработчик не полагается: строки `show_reminders` по адресу
  аккаунта и по `user_id` он удаляет сам, ДО `DELETE FROM users` («меня
  больше нет» включает напоминания; SET NULL остаётся страховкой схемы),
  `marketing_links.created_by` (админ).
- **Не привязано к `users` вовсе** (псевдонимное): `trial_sessions` без
  `user_id` (session_token, ip_hash), `visitors` без `user_id`,
  `guest_checkout_attempts` (HMAC IP гостя или `user:` + HMAC Clerk id —
  #227 — или `idea:` + HMAC IP автора идеи — #297; самопрунинг 2 ч),
  `guest_checkout_sessions` (HMAC cookie `checkout_claim` + id сессии
  Stripe, самопрунинг 24 ч — #224), `stripe_events` (id событий).
- **Кеши**: `roleCache` (5 с, process-local) истекает сам; Data Cache —
  каталог и агрегаты без PII. Чистить нечего.
- **Файлы/медиа**: у пользователей нет загрузок. Чистить нечего.
- **Джобы**: одна — ретеншен-крон `/api/cron/retention` (Vercel Cron, раз в
  сутки, `CRON_SECRET`): только DELETE по окнам §6 батчами ≤1000, в логах и
  ответе — счётчики и имена таблиц (кейс в лог-аудите). Рассылка — ручная
  кнопка в админке, читает `show_reminders` в момент нажатия.
- **Процессоры**: Clerk — источник истины. Stripe — обработчик
  `user.deleted` сам ставит живой подписке `cancel_at_period_end: true`
  (best-effort: сбой Stripe стирание не останавливает, но уходит в лог и
  Sentry по id) и ДО `DELETE FROM users` пишет в тумбстоун
  `erased_customers` `stripe_customer_id` **и все `cus_…`, которые
  `customers.search` находит по адресу аккаунта** (#223: гостевой checkout
  создаёт Customer из адреса на форме, поздняя покупка из-под аккаунта
  перезаписывает id в `users` — старого помнит только Stripe; поиск только
  при платёжном следе — `stripe_customer_id` или строка `subscriptions`,
  иначе адрес аккаунта эпохи free/gate впервые ушёл бы в Stripe; из ответа
  берутся только клиенты с ТОЧНО этим адресом — `:` у Stripe по строковому
  полю матчит и надстройку `a@b.com.mx`, а ложный тумбстоун навечно лишил
  бы чужого покупателя аккаунта; одна страница
  ≤100, 5 с, без ретраев, best-effort; сбой поиска — лог + Sentry по id и
  ручной путь в ранбуке §4, повторить скриптом нельзя: адрес уходит вместе
  со строкой, payload Clerk его не несёт) — без тумбстоуна следующий вебхук
  Stripe по любому из этих клиентов (`guest = "1"` в метаданных не
  истекает) воссоздал бы Clerk-пользователя и `users` с адресом через
  `claimGuestCheckout`; `mirrorSubscription` и `/welcome` спрашивают
  тумбстоун ПЕРЕД claim.
  Stripe Customer (email, billing address) при этом остаётся — `customers.del`
  = решение владельца (`docs/registry.md`). PostHog — тот же `eraseUser`
  ПОСЛЕ локальных DELETE удаляет person по `distinct_id` = Clerk id вместе с
  событиями (`lib/posthog-erase.ts`, #180: `GET persons?distinct_id` →
  `DELETE persons/{id}?delete_events=true&delete_recordings=true` — персона,
  события И записи сессий (replay в проекте включён), 5 с, без ретраев, никогда не
  бросает, тело ответа не читается; типизированный статус — `deleted` /
  `not_found` / `skipped_unconfigured` / `skipped_forbidden` (у personal
  key нет `person:write`) / `failed`; два последних — лог + Sentry по id и
  ручной путь в ранбуке §4; шаг идёт и когда строки `users` уже нет — так
  повтор скрипта добирает PostHog после сбоя). Resend — логи
  истекают через 30 дней сами; Meta/Google/OpenAI держат хешированный email
  и клиентские id событий — per-user удаления у них нет; Sentry — только
  `user.id`, истекает по ретеншену плана.
- **Бэкапы не вычищаем точечно** — позиция ICO «put beyond use»: live-системы
  чистятся сразу; дампы (age-шифрование, приватный Vercel Blob, Франкфурт)
  уезжают ретеншеном 35 дней (`infra/backup/blob.ts prune`); restore из
  бэкапа после erasure → `pnpm erase-user <id> --apply` по каждой строке
  реестра заявок (ранбук §6) со статусом `erased` позже даты дампа — шаг §7
  в `docs/runbooks/db-restore.md` (#180); самообслуживание (приложение,
  #309; UserProfile) в реестр не попадает — его находит там же сверка
  `users` восстановленной базы с Clerk (нет в Clerk → стереть). Neon PITR —
  6 часов, короче любого окна.
- **Устройство пользователя** (cookies, localStorage, SecureStore
  приложения) — вне нашего контроля; `/cookies` объясняет, как удалить.

## Канон портируемости (ст. 20) и доступа (ст. 15)

- **Ранбук — `docs/runbooks/gdpr-requests.md`** (#163): приём на

  ст. 15(1)), реестр заявок без имён — таблица в самом ранбуке. Раздел
  «Адрес без аккаунта» (§2, #339): `pnpm -s export-email` / `erase-email`
  ниже. Раздел
  «Стирание» (§4, #180): два пути (пользователь сам в Clerk / оператор в
  Clerk Dashboard — один вебхук), `pnpm erase-user <id> [--apply]` для
  недошедшего вебхука и restore, ручной PostHog-fallback при
  `skipped_forbidden` / `failed`, таблица «что остаётся у процессоров и
  почему», статус `erased` в реестре — по нему §7 `db-restore.md`.
- **Скрипт — `pnpm export-user-data <userId> [--out <file>]`**
  (`scripts/export-user-data.ts`, логика и тесты в `lib/user-export.ts` +
  `lib/user-export-db.ts`): девять таблиц по ключам карты (`users` по `id`;
  `subscriptions`, `watch_progress`, `watch_days`, `trial_sessions`,
  `visitors` по `user_id`; `visitor_days` по найденным `aid`;
  `show_reminders` по `user_id` **или** `email`; `idea_submissions` — только
  по адресу аккаунта в нижнем регистре, #297) — только Drizzle, без сырого
  SQL; `stripe_events` и `watch_segments` не входят. Вендоры best-effort и
  только при явной переменной: `CLERK_SECRET_KEY` → профиль (с #277 — и
  `externalAccounts`: профили Google / Apple, через которые входил человек),
  `STRIPE_SECRET_KEY` → Customer + инвойсы, `POSTHOG_PERSONAL_API_KEY` +
  `POSTHOG_PROJECT_ID` → персона + события по `distinct_id` = Clerk id (транспорт
  `lib/posthog-hogql.ts`, тот же, что у админки); нет переменной или вендор
  упал → `null` + строка в `notes`, никогда не throw. `.env.local` скрипт не
  читает: `DATABASE_URL` передаётся явно, без него — exit 2. Файл `0600`; в
  stdout — только счётчики (кейс в `lib/log-audit.test.ts`).
- Формат: JSON — «структурированный, машиночитаемый»; отправка —
  зашифрованный архив, пароль отдельным каналом; ссылка с ограниченным TTL,
  когда появится место для приватных объектов.
- Derived-данные (страна, атрибуция, `converted`, флаги дней) в ст. 20 не
  входят, но доступ по ст. 15 шире — выгрузка прикладывает их как есть, а
  письмо помечает, что это ст. 15, не ст. 20. `ip_hash`,
  `stripe_customer_id`, id вендоров — данные субъекта, входят.
- Адрес без аккаунта (`show_reminders` и `idea_submissions` — у автора идеи
  аккаунта может не быть вовсе): `pnpm -s export-email <адрес> [--out <file>]` и
  `pnpm -s erase-email <адрес> [--apply]` (#339; `scripts/export-email.ts` /
  `erase-email.ts`, вся логика и тесты в `lib/address-requests.ts`, ранбук §2).
  Обе таблицы по адресу в нижнем регистре; `DATABASE_URL` явно, без него —
  exit 2; файл `0600`; в stdout и stderr — `address#<8 hex sha256>` (тот же
  хеш, что в реестре заявок ранбука), счётчики и id строк, никогда адрес
  (кейсы в `lib/log-audit.test.ts`, включая сбой базы — класс + SQLSTATE
  через `describeDbError`). Стирание — dry-run по умолчанию, `--apply` удаляет
  обе таблицы ОДНОЙ транзакцией. Адрес, на который заведён аккаунт
  (`users.email` без учёта регистра), отклоняется (exit 4) с id аккаунта и
  отсылкой к `export-user-data` / `erase-user`: у аккаунта ответ полнее
  (таблицы аккаунта, вендоры, тумбстоун). `user_id` другого аккаунта в строках
  `show_reminders` из выгрузки по адресу убирается (ст. 15(4)). Новый код,
  читающий эти таблицы по адресу, берёт ТОТ ЖЕ предикат (`lib/erase-user.ts`
  сверяется тестом в `lib/address-requests.test.ts`). Self-service «скачать мои
  данные» для самого человека — продуктовое решение владельца
  (`docs/registry.md`).

## Инцидент с данными (ст. 33/34) — только эскалация

Признаки: доступ посторонних к Neon, к бэкапам в Blob или к приватному
age-ключу (`BACKUP_AGE_SECRET_KEY` + менеджер паролей владельца), утёкший
`.env.local` (в нём боевые `DATABASE_URL`/`sk_live`), данные пользователей в
открытых логах Vercel, в Sentry, в событиях PostHog/пикселей, письмо не тому
адресату, персональные данные в теле issue/PR/чата агента. Часы (72 ч на
нотификацию SA) тикают с момента **awareness**.

Действия агента: немедленный доклад владельцу (p1, не в дайджесте) + issue
`type:bug` + `domain:infra` + `p1` + зафиксировать таймлайн и масштаб (какие
таблицы/ключи, сколько субъектов — `count(*)`, не списки). Решения
«рисково/не рисково» и нотификации (ICO/AEPD, субъекты) — человек. Любой
инцидент, даже ненотифицируемый, — во внутренний реестр (ст. 33(5)): issue +
строка в post-mortem.
