# DevOps-карта Matio

Снимок на 14.08.2026. Правило: **меняешь инфраструктуру — обновляешь этот
скилл тем же PR** (как `docs/registry.md`). Устаревшая карта хуже её
отсутствия: по ней принимают решения в инциденте.

Детали интеграций и переменных — `docs/services.md`; версионные ловушки
вендоров — `docs/gotchas.md`; этот файл про то, ГДЕ всё живёт и что сломается.

## CI

`.github/workflows/ci.yml` (джоба `web`), GitHub-раннеры, ~3 минуты:
линт → типы → чек токенов (`tools/qa/no-magic-styles.sh`) → установка
chromium → тесты обоих проектов с покрытием → diff-cover ≥85% на изменённых
строках → стики-коммент с покрытием. Голден упал — артефакт
`visual-baselines` с диффами и свежими эталонами.

**Сборки `next build` в CI НЕТ**: её на каждый PR делает preview-деплой
Vercel, и его чек обязателен в ruleset. Если Vercel-чек когда-нибудь
перестанет быть обязательным, сборку надо вернуть в CI.

`.github/workflows/security.yml` — ночью (03:17 UTC) osv-scanner по локфайлам
и gitleaks по всей истории. Сигнал, не ворота: находки → issues.

Ещё два воркфлоу по расписанию — не ворота, а эксплуатация: `db-backup.yml`
(03:40 UTC ежедневно) и `db-restore-check.yml` (1-го числа), см. «Бэкапы».

## Две ступени выкладки

> **Состояние на момент написания**: код двухступенчатой схемы влит, а
> переключение в панелях владелец делает отдельно (issue #40). Пока не создан
> второй проект Vercel, не заведены секреты `VERCEL_TOKEN` / `VERCEL_ORG_ID` /
> `VERCEL_PROJECT_ID` и продовый проект не переведён на ветку `production`,
> воркфлоу выкладки прода спит (гард печатает `::notice::` и пропускает
> выкладку), а мерж в `main` по-прежнему выкладывает прод по-старому. Проверить
> одним взглядом: `gh secret list` и production-ветка в настройках проекта.

```
PR ──► preview (Vercel, без БД: доказывает сборку, и только)
 │
 └─ мерж в main ──► STAGING (свой проект Vercel, своя база, свои ключи)
                       │
                       └─ «релизь» ──► GitHub Release ──► workflow ──► кнопка
                                        владельца ──► ПРОД matio.tv
```

Смысл ступеней: то, что уехало в прод, обязательно постояло на staging.
Отдельно от этого работает правило миграций (см. «БД»).

## Продакшн

`https://matio.tv` (апекс канонический; `www` → 307 на апекс; жив легаси-алиас
`matio-ten.vercel.app`).

**Выкладка — только по опубликованному релизу.** Мерж в `main` прод больше не
трогает: продовый проект Vercel слушает ветку **`production`**, в которую
автоматика не пишет. Публикация GitHub Release запускает
`.github/workflows/deploy-production.yml`; job привязан к GitHub Environment
**`release-production`**, поэтому встаёт и ждёт кнопки владельца, а затем выкладывает
релизный тег через Vercel CLI (`vercel pull` → `build --prod` →
`deploy --prebuilt --prod`) и снимает смоук с `/api/healthz`.

Здоровье: `curl -s https://matio.tv/api/healthz | jq` → `status`, `version`
(из `package.json`, бампает release-please), `commit`, `environment`.
Поле `version` обязано совпасть с созданным тегом без префикса `matio-v`.

### Аварийная выкладка (автоматика сломалась)

Три пути, от дешёвого к грубому. Первый закрывает 90% случаев.

1. **Ручной запуск того же воркфлоу.** Actions → `deploy-production` → Run
   workflow → в поле `ref` тег, ветка или SHA. Кнопка подтверждения в
   Environment остаётся на месте. Это же способ выложить хотфикс без релиза.
2. **Умерли сами Actions** (или воркфлоу невозможно починить): толкнуть коммит
   в продовую ветку руками — `git push --force origin <sha>:production`.
   Продовый проект соберёт её своей git-интеграцией. Это и есть причина, по
   которой ветка `production` вообще существует: рычаг «разбить стекло».
3. **Откат без сборки**: Vercel → проект `matio` → Deployments → предыдущий
   продовый деплой → **Promote to Production**. Сборки нет, алиас
   переключается за секунды — самый быстрый способ погасить пожар.

Чего делать НЕ надо: `vercel --prod` с машины владельца залипает в BLOCKED
(см. «Грабли») — на этот путь не рассчитывать.

**Ветка `production` автоматикой не двигается.** Если бы воркфлоу её толкал,
Vercel собрал бы тот же коммит второй раз, и две продовые сборки поехали бы
наперегонки за один алиас. Что реально живо на проде — отвечает `/api/healthz`,
а не эта ветка.

## Staging

Тренировочная площадка: **отдельный проект Vercel на том же репозитории**,
production-ветка `main` — то есть мерж PR выкладывает именно её. Адрес —
служебный `matio-staging.vercel.app` (свой поддомен намеренно не заводили: DNS
не трогаем).

### Как зайти на стенд

Обычный HTTP Basic Auth: браузер спросит логин и пароль, **логин любой**,
пароль — в менеджере паролей владельца (запись «matio staging»). В репозитории
пароля нет и быть не может: он живёт только в переменной окружения
`STAGING_LOCK_PASSWORD` **проекта стенда**.

- **На проде переменную не задавать никогда.** Пустая или отсутствующая —
  замка нет, и это ровно то поведение, которое должно быть у `matio.tv`.
- Переменные Vercel привязываются на **деплое**: задал/убрал → **редеплой**,
  иначе ничего не изменится.
- Открыт без пароля только `/api/healthz` — смоук релизного воркфлоу и
  аптайм-проверки не должны носить с собой пароль, а данных в ответе нет.
  Всё остальное, включая `/api/t`, отдаёт `401` с
  `WWW-Authenticate: Basic realm="matio staging"`.
- Пока замок включён, **каждый** ответ несёт `X-Robots-Tag: noindex, nofollow`
  — второе дно против индексации стенда (401 и так не индексируется).
- Замок закрывает то, что проходит через `proxy.ts`. Статика `_next/*` и файлы
  по расширению исключены его matcher'ом и отдаются без пароля — угадывать имена
  чанков бессмысленно, персональных данных и секретов там нет.
- `curl` для проверки: `curl -sI https://matio-staging.vercel.app/` → `401`,
  `curl -sI -u x:<пароль> https://matio-staging.vercel.app/` → `200`.

**Почему замок в приложении, а не в панели.** Vercel Authentication закрывает
служебные адреса, но чтобы закрыть **основной алиас проекта**, ей нужен
`deploymentType: "all"` — а тариф отвечает
`428 Vercel Authentication is not available on your plan for production
deployments`. Бесплатный уровень (`prod_deployment_urls_and_all_previews`)
основной адрес не трогает, а стенд — это production-деплой своего проекта.
Отсюда решение владельца из #40: «простой пароль» в самом приложении
(`lib/staging-lock.ts` + первая же проверка в `proxy.ts`, до всей маркетинговой
машинерии — иначе случайный заход минтил бы куки посетителя и строки
атрибуции). Появится тариф Pro или собственный домен со своей защитой —
переменная убирается, код остаётся.

Правила стенда (нарушение каждого стоит боевых данных):

- **Данные — только сид, никакой копии прода.** Ни аккаунтов, ни подписок, ни
  истории просмотра, ни адресов из формы напоминаний. Наполнение:
  `pnpm seed:fake-shows -- --playback-ids=<mux id>[,<id>:<секунды>]` — 35
  демо-шоу, у одного из них сезон с играющими эпизодами.
- **Стенд только СМОТРИТ в Mux.** Аккаунт Mux общий с продом, ассеты
  принадлежат аккаунту: заливка со стенда съест слот из десяти на бесплатном
  плане, а вебхук о готовности прилетит на `matio.tv`. «Уборка тестовых видео»
  на стенде уничтожит боевые. В базе стенда лежат только указатели
  (`mux_playback_id`), файлы не копируются.
- **Свой ключ подписи Mux** (второй ключ в том же аккаунте). Продовый не
  копировать: утёкший ключ стенда отзывается одной кнопкой, не роняя сайт.
  Он же снимает будущее ограничение продового ключа по домену `matio.tv`.
- **Аналитика молчит**: `NEXT_PUBLIC_POSTHOG_KEY`, `NEXT_PUBLIC_GA_MEASUREMENT_ID`,
  `NEXT_PUBLIC_META_PIXEL_ID(S)`, токены CAPI и `NEXT_PUBLIC_MUX_DATA_ENV_KEY`
  на стенде **пустые**. Тестовые клики в боевом дашборде задним числом не
  чинятся.
- **Письма выключены**: `RESEND_API_KEY` пустой.
- **Вебхуков у стенда нет**: Stripe/Clerk/Mux шлют на `matio.tv`, секреты
  подписи разные, чужое событие стенд не обработает и не должен.
- **Ступень называет переменная `APP_ENV`**: на проекте стенда она задана в
  `staging`, на проде **не задана никогда**. `/api/healthz` отдаёт
  `environment` из неё, а без неё — из `VERCEL_ENV` (прежнее поведение, и
  именно оно верно для прода). Маркер понадобился потому, что `VERCEL_ENV`
  для production-ветки ЛЮБОГО проекта Vercel равен `production` — стенд
  называл себя продом и по этому полю от `matio.tv` не отличался. Переменная
  привязывается на **деплое**: задал → редеплой, иначе healthz продолжит
  отвечать по-старому. Проверка:
  `curl -s https://matio-staging.vercel.app/api/healthz | jq -r .environment`
  → `staging`, то же на `matio.tv` → `production`.

`vercel.json` (регион `fra1`, `framework: nextjs`, заголовки) лежит в
репозитории и потому **общий для обоих проектов** — различия между стендом и
продом задаются только переменными окружения и настройками проекта в панели,
никогда этим файлом.

`"framework": "nextjs"` там стоит из-за стенда: проект, созданный через CLI, не
получает метку фреймворка, и его первая сборка упала на «No Output Directory
named dist» — Vercel искал статику вместо того, чтобы отдать сборку адаптеру
Next. В панели это поправлено разово; поле в `vercel.json` держит настройку в
репозитории, чтобы следующий git-деплой стенда не упал снова. Проду поле
безвредно: у него та же метка уже стоит на проекте.

Preview-деплои на PR даёт **продовый** проект: именно его чек `Vercel` стоит
обязательным в ruleset `protect-main`. Выключишь у него git-интеграцию —
перестанут вливаться все PR.

## БД

Neon, пулер, Drizzle. Миграции: `pnpm db:generate` → `pnpm db:migrate`.
`db:push` против прода — **никогда**.

**Порядок: сначала staging, потом прод.** Ради этого площадка и заводилась.

1. `DATABASE_URL=<ветка staging> pnpm db:migrate` — миграция на стенде;
2. проверить на стенде то, что она трогает (страницу, вебхук, админку);
3. мерж в `main` → стенд обновился кодом, миграция уже стоит;
4. `pnpm db:migrate` против прода — **до** релиза, если миграция аддитивная;
5. релиз → кнопка → прод.

Удаление колонки — только ПОСЛЕ того, как деплой без неё стал READY (Drizzle
запекает полный список колонок в сборку, и `SELECT *` по исчезнувшей колонке
роняет прод — это уже стоило трёхминутного простоя 04.06.2026). Со стендом
этот порядок наконец есть где отрепетировать.

## Бэкапы

Свои шифрованные дампы **вне Neon** + автоматическая проба восстановления
(этап 06 плейбука, issue #35). PITR у Neon остаётся быстрым слоем «ой, удалил
не то», но бэкапом больше не считается.

| | |
|---|---|
| Что | `pg_dump -Fc` боевой базы, шифрование **age**, объект в Vercel Blob |
| Где | стор `matio-blob`, префикс `db-backups/production/`, объекты **приватные** (`access: 'private'`) — по голому URL не отдаются |
| Когда | `db-backup` ежедневно в 03:40 UTC + ручной запуск |
| Ретеншен | **35 дней, руками скрипта**: у Blob НЕТ lifecycle-правил S3/R2. Уборку делает `infra/backup/blob.ts prune`, и самый свежий объект она не удаляет никогда |
| Проба | `db-restore-check` 1-го числа в 04:20 UTC: последний дамп → чистый Postgres 18 (`services:`) → smoke по `drizzle.__drizzle_migrations`, `shows`, `episodes`, `users` → строка «OK: restore-проба пройдена (…)» |
| Свежесть | проба валится, если последнему дампу больше 48 ч — мёртвый `db-backup` не может пролежать незамеченным месяц |
| Ключ | приватный age-ключ — в менеджере паролей владельца И в секрете `BACKUP_AGE_SECRET_KEY`; публичный — в переменной `BACKUP_AGE_PUBLIC_KEY`. Третьей копии нет: потеряны обе — дампы мусор |
| Секреты | `BACKUP_DATABASE_URL` (**прямой, не пулерный** эндпоинт Neon — через пулер pg_dump не работает), `BLOB_READ_WRITE_TOKEN`, `BACKUP_AGE_SECRET_KEY` |
| Провал планового прогона | воркфлоу сам заводит p1-issue (`domain:infra`), повторный провал — комментарием в неё. На доску её кладут руками |
| Восстановление руками | `docs/runbooks/db-restore.md` — по шагам с командами |

Чего в бэкапе нет: **артворк шоу в Vercel Blob и видео в Mux**. В базе только
ссылки на них; потеря стора = каталог без постеров, потеря аккаунта Mux =
каталог без видео.

Гарды обоих воркфлоу устроены асимметрично намеренно: ручной запуск без
секретов печатает их ИМЕНА и мягко пропускается, а **плановый** — падает.
Настроенный бэкап, который каждую ночь тихо не идёт, ничем не лучше
отсутствующего.

## Наблюдаемость

Sentry (ошибки сервера, edge и браузера + 10% трейсов) плюс две ручки здоровья.
Этап 07 плейбука, issue #36.

### Где живёт DSN и как он включается

Переменная одна — **`NEXT_PUBLIC_SENTRY_DSN`**, и она же выключатель: не задана
→ `Sentry.init` не вызывается ни на одном рантайме, обёртка `withSentryConfig`
не применяется, браузер не скачивает ни байта SDK. Это позволило влить код до
регистрации аккаунта.

- **`NEXT_PUBLIC_*` инлайнится на СБОРКЕ, в том числе в серверном бандле.**
  Задать переменную в панели и не сделать редеплой = ничего не изменилось. Та же
  грабля, что у `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY`.
- DSN — не секрет (он публичный по устройству), но живёт в переменных проекта, а
  не в репозитории.
- Ступень события берётся из той же логики, что `/api/healthz`: `APP_ENV` →
  `VERCEL_ENV` → `development` (`resolveStage` в `lib/observability.ts`). На
  клиенте видны только `NEXT_PUBLIC_*`, поэтому браузерным событиям нужен свой
  **`NEXT_PUBLIC_APP_ENV=staging`** на проекте стенда — без него события стенда
  из браузера уедут в `production` (`NEXT_PUBLIC_VERCEL_ENV` у стенда тоже
  `production`).
- `release` = `APP_VERSION`, то есть версия из `package.json`, которую бампает
  release-please, — ошибка привязана к тегу релиза.
- Опционально `SENTRY_ORG` / `SENTRY_PROJECT` / `SENTRY_AUTH_TOKEN` — загрузка
  карт исходников на сборке. Без токена сборка печатает предупреждение и идёт
  дальше; сами карты после загрузки удаляются из выкладки.

### Приватность — не настройка, а причина ручной установки

Визард Sentry ставит Session Replay и виджет обратной связи: первый пишет DOM
(экран зрителя, поля форм), второй собирает имя и адрес. У нас нет ни того, ни
другого, плюс `sendDefaultPii: false`, `includeLocalVariables: false`,
`enableLogs: false` и хуки `beforeSend` / `beforeSendTransaction` /
`beforeBreadcrumb`, которые срезают query-строки и креды из URL, удаляют куки,
тело запроса и разобранный query, оставляют из заголовков только белый список,
сводят пользователя к id, вымарывают адреса из текстов и **целиком выбрасывают
console-брэдкрамбы**. Всё это — в `lib/observability.ts`, под тестами
(`lib/observability.test.ts`) и тест-аудитом логов (`lib/log-audit.test.ts`).
Трогаешь этот файл — доказывай тестом.

Туннеля через свой роут нет: события идут на Sentry напрямую. У нас уже есть
`/ingest` для PostHog, а потерянный из-за блокировщика отчёт об ошибке — наша
потеря, не зрителя.

### `/api/healthz` и `/api/readyz`

| | `/api/healthz` | `/api/readyz` |
|---|---|---|
| Отвечает на | «жив ли процесс и какая это сборка» | «может ли эта выкладка работать» |
| Ходит в БД | **никогда** (намеренно) | `select 1` в Neon, потолок 2 с |
| Тело | status, version, commit, environment | только статус и длительность пинга |
| Код | всегда 200 | 200 / **503** (`timeout`, `unavailable`, `not_configured`) |
| На стенде | открыт без пароля | **закрыт паролем** — в белом списке замка только healthz |

**Зелёный `/readyz` НЕ доказывает, что сервис обслуживает клиентов.** Проба
берёт своё соединение под свой дешёвый запрос: исчерпание пула, деградация
пулера, залипшие транзакции — отказ обвальный и для такой проверки невидимый.
Ручка отвечает на «БД вообще отзывается», и только.

`not_configured` — отдельный ответ не для красоты: `db/index.ts` это ленивый
Proxy, клиент создаётся на ПЕРВОМ запросе, и выкладка без `DATABASE_URL`
(preview у Vercel) прекрасно живёт, пока кто-нибудь не спросит. Без этой ветки
получился бы безымянный 500 вместо «этой выкладке базу не выдавали».

Проверить руками: `curl -s https://matio.tv/api/readyz | jq` → `status: "ok"`.
Локально красноту видно так: `DATABASE_URL="postgres://x:y@127.0.0.1:5433/z"
PORT=3210 pnpm start` → `curl -s http://127.0.0.1:3210/api/readyz` отдаёт 503 с
`reason: "unavailable"`, а `/api/healthz` при этом остаётся 200 — ровно то
разделение, ради которого ручки две.

### Инциденты

Всплеск ошибок в Sentry или красный ночной прогон — это **issue**, а не
воспоминание: `gh issue create` (`type:bug`, приоритет по влиянию) +
`tools/claude/board_status.sh <N> …`. Правило записано в CLAUDE.md; смысл тот
же, что у `docs/registry.md`: находка, которой нет на доске, не существует.

## Релизы

`release-please` держит один Release PR; мерж = тег `matio-vX.Y.Z` + GitHub
Release + бамп `package.json`. Ритуал — скилл `/release`. Мержит только
основная сессия и только по «релизь».

**Релиз = выкладка прода.** Публикация Release запускает
`deploy-production.yml`, тот ждёт кнопки в Environment `release-production` и едет.
Поэтому пре-релизные проверки на staging — не формальность, а последний
момент, когда что-то ещё можно остановить.

## Грабли (проверены кровью — не переоткрывать)

0.0. **Собрать приложение ВНЕ Vercel невозможно.** 34 из 42 продовых
   переменных хранятся как `Encrypted`, и `vercel pull` их значения НЕ
   отдаёт — они доступны только на запись. Сборка в раннере получает пустые
   значения, а `NEXT_PUBLIC_*` инлайнятся в бандл на этапе сборки. Инцидент
   #46 (04.08.2026): пустой `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` → Clerk-мидлвар
   бросает «Missing publishableKey» на КАЖДОМ запросе → 500 на всём сайте,
   включая `/api/healthz`. Прод лежал ~12 минут. Поэтому `deploy-production.yml`
   загружает исходники, а собирает Vercel своим окружением. `vercel build` +
   `--prebuilt` в этом проекте не использовать никогда.

0. **Окружения `Production` и `Preview` в этом репозитории принадлежат
   интеграции Vercel** (созданы ботом 10.05.2026 — через них он отмечает свои
   деплои). Имена окружений GitHub уникальны БЕЗ учёта регистра, поэтому
   попытка завести своё окружение `production` молча правит чужое. Наш
   релизный шлюз живёт в отдельном `release-production`; секреты выкладки — в
   нём же. Проверено при настройке 31.07.2026: правило подтверждения,
   ошибочно повешенное на `Production`, деплои Vercel не заблокировало —
   но полагаться на это нельзя.

1. **`vercel --prod` с этой машины залипает в состоянии BLOCKED.** Выкладка —
   через релиз (или его ручной запуск), а не с ноутбука. `git push` при этом
   остаётся единственным бэкапом кода.
2. **DROP COLUMN только после READY-деплоя без неё** (см. «БД»).
3. **Preview-окружение без `DATABASE_URL`**: сборка проходит благодаря
   ленивому `db/index.ts`, но всё, что реально ходит в БД, на preview не
   работает. Не считать зелёный preview доказательством работоспособности.
4. **Mux: 10 ассетов на бесплатном плане.** Симптом — обычная маскированная
   ошибка server action в админке при загрузке видео.
5. **`git add -A` на ветке от main** тянет `mobile/` целиком: `mobile/.gitignore`
   существует только в ветке `feat/mobile-app`. Корневой `.gitignore`
   закрыт (`node_modules/`, `.expo/`), но привычку добавлять пути явно
   стоит сохранить.
6. **Стухший `.next` от другой ветки роняет `pnpm typecheck`** на
   `.next/dev/types/validator.ts` — лечится `rm -rf .next`.
7. **Локальный `grep` на машине владельца — ugrep**, у него другая
   семантика `--include`; в скриптах отбирать файлы через `find`.
8. **Голден-расхождение приезжает как «Test timed out in 15000ms»**, а не
   как «screenshot mismatch» (см. `lab/golden.ts`).
9. **Секреты никогда не постить в issues/PR**; фейковые секреты в тестах
   должны выглядеть фейково (`sk-test-…`, dummy) — иначе их пометит ночной
   gitleaks.
10. **`vercel.json` общий для обоих проектов** (один репозиторий). Различать
    стенд и прод им нельзя: `git.deploymentEnabled` там выключил бы деплой
    сразу у обоих. Различия — только в переменных и настройках проекта.
11. **Не выключать git-интеграцию продового проекта.** Его preview-деплой —
    обязательный чек `Vercel` в ruleset `protect-main`: без него не вливается
    НИ ОДИН PR, включая тот, которым это чинят.
12. **Клиент Postgres в CI обязан быть того же мажора, что сервер (18).**
    Debian-обёртка `/usr/bin/pg_dump` выбирает СИСТЕМНУЮ версию, а на раннере
    предустановлен 16-й — дамп он снимать откажется. Оба backup-воркфлоу ставят
    `postgresql-client-18` из PGDG и пиннуют реальные бинарники
    (`echo "/usr/lib/postgresql/18/bin" >> $GITHUB_PATH`), а скрипты печатают
    `pg_dump --version` в лог: через полгода это первая строка, по которой
    расследуется «дамп не восстанавливается».
13. **Порядок переключения на двухступенчатую схему важен.** Сначала завести
    стенд и секреты, проверить выкладку прода ручным запуском воркфлоу — и
    только потом переводить продовый проект на ветку `production`. Наоборот
    получается окно, в котором прод нечем выложить вообще.
