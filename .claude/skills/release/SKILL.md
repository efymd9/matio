# Релизный ритуал

**ЖИВОЙ документ**: изменились пороги, шаги ритуала или механика
release-please → обнови этот скилл ТЕМ ЖЕ PR.

## Железные правила

- Release PR мержит **только основная сессия** и **только по явному
  «релизь» от владельца**. Авто-мерж на Release PR не взводить никогда.
- Release PR (`release-please--branches--main`) аккумулирует changelog сам
  после каждого мержа в main — его не трогать руками, в его ветку не
  коммитить.
- Версия одна на весь продукт: тег **`matio-vX.Y.Z`** + `package.json` +
  `CHANGELOG.md` (бампает бот). До 1.0.0 `feat:` даёт минор, а не мажор.
  Префикс `matio-` добавляет сам release-please в manifest-режиме
  (`include-component-in-tag` по умолчанию включён). Хотим голое `vX.Y.Z` —
  выставить его в `false`, но проверять на СЛЕДУЮЩЕМ релизе: бот ищет
  предыдущий тег, чтобы посчитать диапазон changelog, и смена схемы
  именования — ровно тот случай, когда он может его не найти.
- **Релиз — единственная дверь в прод.** Мерж в `main` выкладывает staging;
  `matio.tv` обновляется только тогда, когда опубликован GitHub Release и
  владелец нажал кнопку подтверждения в Environment `production`. Мерж
  Release PR больше НЕ безопасное событие «только версия и changelog»: он
  публикует релиз, а тот запускает выкладку прода. Всё, что уезжает, обязано
  до этого постоять на staging.

## Конвенция коммитов

`fix:` → патч · `feat:` → минор · `feat!:` / `BREAKING CHANGE:` → мажор ·
`docs:` попадает в changelog · `chore:`/`ci:`/`test:` скрыты. Тип коммита —
не украшение, а то, из чего собираются версия и changelog.

## Пре-релизный ритуал (по порядку; пункты со «*» — если модуль внедрён)

1. **Изменения проверены на staging — ОБЯЗАТЕЛЬНО.** Всё, что накопил Release
   PR, уже стоит на стенде (мерж в `main` его туда и выложил). Открыть стенд и
   прокликать то, что этот релиз меняет: воспроизведение эпизода на
   `/watch/<slug>`, испанская версия `/es`, вход в админку. Плюс — миграции: у
   каждой миграции этого релиза должен быть прогон на ветке staging ДО прода
   (порядок — в скилле `/devops`). Не проверено на стенде → релиза нет; чинить
   после нажатия кнопки будет уже на зрителях.
   *Пока стенд не заведён (issue #40) — проверять на проде, как раньше, и
   помнить, что код там уже живой.*
2. **Реестр хвостов**: `docs/registry.md` — нет ли пунктов «сделать перед
   продом», блокирующих именно этот релиз.
3. **CI на Release PR зелёный.** Если он вообще не запускался — почти
   наверняка отвалился GitHub App (см. «Грабли»): без чеков ruleset PR не
   пропустит.
4. **E2E*** — не внедрено. Появится e2e-прогон — сюда придёт шаг «дождаться
   зелёного».
5. **Перф-рэтчет*** — не внедрено (этап 09 плейбука).

## Мерж и пост-релиз

1. По «релизь»: `gh pr merge <Release PR> --squash` (основная сессия).
2. Бот создаст тег + GitHub Release; проверить: `gh release list -L 1`.
   Первый релиз (`matio-v0.2.0`, 31.07.2026) прошёл ровно по этому ритуалу.
3. **Нажать кнопку.** Публикация Release запускает `deploy-production.yml`;
   job встаёт в Environment `production` и ждёт подтверждения: Actions → прогон
   → **Review deployments** → Approve. Без нажатия прод не поедет — это и есть
   санкция владельца, зафиксированная механически.
4. Дождаться конца прогона и снять смоук:
   ```
   curl -s https://matio.tv/api/healthz | jq
   ```
   Поле `version` обязано совпасть с созданным тегом (без префикса `matio-v`).
   Тот же смоук делает и сам воркфлоу — красный шаг «Смоук /api/healthz»
   означает, что релиз объявлен, а на сайте старый код. Разбираться ДО того,
   как объявлять релиз состоявшимся; быстрый откат — Promote предыдущего
   продового деплоя в Vercel (см. `/devops`).
5. Доска: закрытые релизом issues уехали в Done (обычно сами через
   `Closes`); пробежать `gh issue list --search "is:open"` на предмет
   зависших.
6. Менялись пороги/карты — обновить эталонные issue и скиллы тем же днём.

## Грабли

- **Release PR создаётся от имени GitHub App, а не GITHUB_TOKEN**: PR от
  GITHUB_TOKEN не запускают workflow (ограничение GitHub) — CI на Release PR
  не стартует, а в ruleset `protect-main` чеки обязательны, значит влить его
  будет НЕЛЬЗЯ. После переносов/пересозданий репозитория проверять установку
  приложения (`gh api repos/efymd9/matio/installation`), иначе release-please
  молча падает по авторизации.
- Squash-мерж «сжигает» ветку Release PR — бот пересоздаст следующий сам.
- **Релиз = выкладка на прод.** Релиз в пятницу вечером или перед сном не
  делаем: и кнопку нажимать, и пост-релизную сверку смотреть некому.
- **Забытая кнопка выглядит как «релиз не доехал».** Job в Environment ждёт
  подтверждения молча — если `/api/healthz` отдаёт старую версию, сначала
  проверить, не висит ли прогон в состоянии Waiting.
- Мобильное приложение (issue #17) живёт вне main и в версионирование пока
  не входит. Когда вольётся — добавить `mobile/app.json` в `extra-files`
  конфига release-please, иначе версия приложения разъедется с продуктовой.
