# Этап 09 — Нагрузочное тестирование (опциональный модуль)

## Что вы получите

Умение отвечать числами на вопросы «сколько пользователей выдержим» и «стал
ли релиз медленнее»: k6-сценарии, методику зачётных прогонов (без неё цифры
врут), паспорт ёмкости и перф-рэтчет в релизном ритуале. Модуль оправдан,
когда у продукта есть постоянные соединения / реальный трафик / деньги на
стенды; до этого — пропускайте смело.

## Что делает человек

1. Примите бюджетное правило: **стенд — платный и временный**. Типовая
   кампания оригинала укладывалась в ≤$30; стенд создаётся по вашей
   команде и гасится сразу после прогонов (managed-БД тикает и у
   погашенного стенда!).
2. Все команды «подними стенд», «запусти 12-часовой прогон», «снеси» —
   только ваши, явно. Впишите это в правила при внедрении.
3. Скормите промпт.

## Промпт для агента

```
Внедри модуль нагрузочного тестирования по плейбуку docs/mega-process/
(этап 09). Работай веткой + PR; платные действия (создание стендов,
машин, managed-БД) — только по моей явной команде, каждое — с оценкой
$/сутки до запуска.

1. Скилл: скопируй docs/mega-process/skills/load-campaign/SKILL.md в
   .claude/skills/load-campaign/SKILL.md, замени {{PROJECT}}. Прочитай
   его ЦЕЛИКОМ — методика и грабли там; ниже только состав работ.
2. tools/load/: k6-сценарий главного пользовательского пути (для
   чат-продукта — пары клиентов: логин, постоянное соединение, обмен
   сообщениями, чтение истории; для request/response-продукта — сессии с
   реалистичным миксом ручек). Требования: детерминированные роли по
   индексу виртуального пользователя; параметр OFFSET для раскладки на
   несколько генераторов; пороги зачёта (p95 ключевых операций, доля
   ошибок) — в конфиге, зафиксированы один раз.
3. Сидер тестовых данных (CLI сервера): создать N пользователей/сущностей
   с историей; предохранитель от запуска на непустой «живой» БД; домен
   сид-пользователей — поддомен реальной зоны (не .test/.local — строгие
   email-валидаторы их отвергают).
4. Наблюдаемость прогона: сэмплер метрик сервера (раз в 60 с в CSV) и
   сборщик логов — отдельными процессами, не внутри k6; серверные
   латентности в структурированных логах (это арбитр — k6 при тысячах VU
   врёт, см. скилл).
5. Конфиг стенда: одноразовый клон staging (отдельные приложения/БД) на
   выделенных ядрах — burstable для замеров бесполезен (цифры плывут);
   генераторы — отдельные машины в том же регионе, заведомо мощнее
   испытуемого.
6. docs/: страница «паспорт ёмкости» (таблица: конфигурация → потолок →
   дата → SHA) + эталонный issue под числа. В скилл /release добавь шаг
   перф-рэтчета: зачётный ramp-прогон на пороге паспорта перед релизом
   (стенд — по команде владельца).
7. Первую кампанию проведи по скиллу /load-campaign: прогревочный прогон,
   зачётные ступени, пульсы в issue, отчёт с вердиктом и доказательством
   «упёрся сервер, а не стенд». Каждая находка — отдельный issue, не
   молчаливый фикс.
```

## Критерии готовности

- [ ] k6-сценарий и сидер в репо; пороги зачёта зафиксированы в конфиге.
- [ ] Проведена первая кампания: в issue — пульс-таблица, финальный отчёт
      с вердиктом PASS/FAIL, названным упором и доказательством «сервер,
      не стенд».
- [ ] Паспорт ёмкости существует и назван в /release (перф-рэтчет).
- [ ] Стенд после кампании погашен/снесён; в /devops — актуальная строка
      о его состоянии.

## Бюджетные развилки

- **Эконом**: не заводить модуль вовсе, пока нет постоянных
  соединений/трафика. Промежуточный вариант: разовый прогон на локальной
  машине против локального сервера — грубо, но ловит утечки памяти и
  квадратичные ручки бесплатно.
- **Как у оригинала**: стенды по классам (перф-стенд для рэтчета,
  endurance для многочасовых, отдельный для экспериментов с лимитами),
  живой паспорт с двумя потолками (штормовой для hard_limit и устойчивый
  для сайзинга), перф-рэтчет перед каждым релизом. Триггер: продукт
  держит тысячи постоянных соединений и деградация — это инцидент, а не
  курьёз.
- Главные оплаченные кровью выводы (детали в скилле): первый прогон дня —
  прогревочный, в зачёт не идёт; арбитр латентности — логи сервера, не
  генератор; edge-прокси хостинга режет ~5к TLS-соединений с одного IP —
  шторм только с нескольких машин; лимиты прокси-слоя задавать явно
  (дефолт fly-proxy = невидимая стена 8192 соединений).
