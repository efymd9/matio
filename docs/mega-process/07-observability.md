# Этап 07 — Наблюдаемость: Sentry без утечек приватного

## Что вы получите

Ошибки и трейсы сервера и приложения в Sentry (бесплатный план, данные в
ЕС), причём настроенные так, что туда **физически не попадают данные
пользователей** — токены, query-строки, тексты. Плюс `/healthz`/`/readyz`
и правило «инциденты начинаются с трекера»: красный ночной прогон или
всплеск ошибок — это issue, не воспоминание.

## Что делает человек

1. Зарегистрируйтесь на sentry.io. **При создании организации выберите
   регион данных EU** — потом регион не меняется, только пересозданием
   организации (грабля, которую дешевле не наступать).
2. Создайте два проекта: `<project>-server` (платформа вашего сервера) и
   `<project>-app` (платформа приложения). Скопируйте оба DSN.
3. DSN — не секрет в строгом смысле, но серверный удобнее держать в
   секретах приложения хостинга: `fly secrets set SENTRY_DSN=…` (агент
   подскажет). Для интеграции агента с Sentry (смотреть ошибки из сессии)
   можно позже подключить Sentry MCP — отметьте себе, это опционально.
4. Скормите промпт.

## Промпт для агента

```
Подключи наблюдаемость по плейбуку docs/mega-process/ (этап 07).
DSN спроси у меня, когда дойдёшь. Работай веткой + PR.

1. Сервер — Sentry SDK: environment (staging/prod из env), release =
   APP_VERSION (та же версия, что в /healthz — тогда ошибки привязаны к
   релизам), traces_sample_rate скромный (0.1), и ГЛАВНОЕ — приватность:
   - send_default_pii=False;
   - before_send и before_send_transaction, срезающие query-строки из URL
     (ГРАБЛЯ, оплаченная оригиналом: токены/коды из query-параметров
     утекали в трейсы, пока их не начали срезать хендлером);
   - локальные переменные фреймов в событиях — выключить
     (include_local_variables=False или эквивалент SDK);
   - в логах и breadcrumbs — только id, статусы, длительности.
2. Приложение — Sentry SDK аналогично: environment по флейвору, release =
   версия сборки, send_default_pii=False, никаких текстов пользователя в
   breadcrumbs.
3. /healthz (уже есть с этапа 05: status + version) и /readyz (реальная
   готовность: ping БД и кеша). В CLAUDE.md/skill devops зафиксируй
   честное ограничение: зелёный /readyz НЕ доказывает, что сервис
   обслуживает клиентов — отказ по соединениям обвальный и для
   health-чека невидимый.
4. CLAUDE.md — усилить раздел «Приватность» (если пуст с этапа 01):
   данные пользователей (тексты, контент, профили) НИКОГДА не пишутся в
   логи, Sentry и аналитику; в логах — только id, статусы, длительности.
   Заведи тест-аудит: тест, который прогоняет ключевые пользовательские
   потоки и проверяет, что в перехваченных логах нет маркерных строк
   (посей в тесте узнаваемый текст пользователя и проверь его отсутствие).
5. Правило инцидентов в CLAUDE.md: всплеск ошибок Sentry / красный ночной
   прогон → gh issue create (type:bug, severity по влиянию) — находки не
   живут в памяти и чатах.
6. Проверка: брось тестовое исключение на staging (временная ручка или
   консоль), покажи мне событие в Sentry: release/environment проставлены,
   query-строк и PII нет. Обнови /devops (раздел «Аккаунты»: Sentry) тем
   же PR.
```

## Критерии готовности

- [ ] Тестовая ошибка сервера видна в Sentry с правильными
      release/environment; в URL событий нет query-строк.
- [ ] Тестовая ошибка приложения видна во втором проекте.
- [ ] Тест-аудит логов существует и падает, если посеять текст
      пользователя в лог.
- [ ] `/readyz` желтеет/краснеет при погашенной БД (проверить локально).
- [ ] Организация Sentry — в регионе EU (Settings → Region).

## Бюджетные развилки

- **Эконом**: бесплатный план Sentry (квоты хватает маленькому проекту с
  запасом), без алёртинга наружу — сигналом служат issues от ночных
  workflow и просмотр Sentry при разборах.
- **Как у оригинала**: то же + Sentry MCP в сессии агента (разбор
  инцидента начинается с «посмотри в Sentry» без выхода из чата). Платный
  Sentry — когда упрётесь в квоту событий или понадобятся команды.
- **Статус-страница вне вашей инфры** (опционально): Cloudflare Worker на
  бесплатном плане — cron раз в минуту пингует /healthz, состояние держит
  в Durable Object, отдаёт status.<домен>; гистерезис (N фейлов подряд →
  degraded, M успехов → ok), ручной override на время работ. Смысл: когда
  инфраструктура лежит, страница «у нас всё лежит» обязана жить в другом
  месте. У оригинала это ~100 строк воркера; заводите, когда появятся
  пользователи, которым нужно что-то сообщать.
