# Ревью PR: чеклист основной сессии

**ЖИВОЙ документ**: изменились правила проекта, пороги покрытия или
механика мержа → обнови этот скилл ТЕМ ЖЕ PR.

Мержит **только основная сессия**; агент свой PR не мержит никогда.
Ревью запускается событием вотчера очереди (`tools/claude/pr_watcher.sh`)
или командой владельца.

## Порядок

1. **Первым действием — доска**: `tools/claude/board_status.sh <N> review`
   (номер issue — из `Closes #N` в теле PR; нет `Closes #N` у задачи с
   issue — уже замечание).
2. **Тело PR читать как отчёт** — это единственный канал агента к
   ревьюеру (его сессию ты не видишь; отчёт в чате владельца — не замена).
   В теле должно быть: что сделано и почему · как проверено (команды,
   устройства, прогоны) · соответствие критериям приёмки **по пунктам** ·
   что осознанно отложено (+ строки в `docs/registry.md`). Пустое или
   формальное тело — замечание в тред, не домысливание за агента.
3. **Критерии приёмки** — из спеки в issue (`gh issue view N`): каждый
   пункт проверяем командой/числом, «не на веру» (шаблон — скилл `/spec`).
   Заявленное «проверено» с командой — можно верить; без команды — прогнать
   самому или спросить в треде.
4. **CI зелёный целиком** — красный CI ревью не проходит, ждать нечего:
   коммент в тред, агента будит его вотчер.
5. Дальше — чеклист диффа (`gh pr diff <PR>`).

## Чеклист диффа (по правилам проекта; сверяй с CLAUDE.md своего репо)

- **Контракт**: менялись REST-ручки или realtime-события → спека контракта
  перегенерена из кода, клиент приложения перегенерён (`./tools/gen_api.sh`),
  протокол-документ обновлён. Генерённые файлы не правлены руками.
- **Миграции**: только expand-contract — никаких DDL, ломающих предыдущую
  версию кода, в одном релизе с этим кодом. Индекс на потенциально большой
  таблице обычным `CREATE INDEX` — блокировка записи на всё время
  построения; трейд-офф атомарный/CONCURRENTLY фиксировать комментарием в
  миграции.
- **Приватность**: данные пользователей (тексты, контент, персональное)
  НЕ попадают в логи, трекер ошибок и события аналитики — в новых
  log/capture/track только id, статусы, длительности.
- **Данные** (после этапа 10): новое поле/таблица/кеш-ключ с данными
  пользователя, новый внешний сервис или изменение LLM-промптов/пушей/писем
  → прогнан чеклист `/gdpr`; карта данных и таблица процессоров обновлены
  ТЕМ ЖЕ PR.
- **i18n** (если приложение локализовано): ни одной захардкоженной
  пользовательской строки; новая строка = ключ во всех локалях.
- **UI-токены** (после этапа 04): в фичах приложения нет прямых
  цветов/шрифтов/числовых отступов — только токены темы и компоненты ядра.
- **Тесты утверждают поведение**: asserts на результат/состояние/ошибку;
  тест, исполняющий строки ради процента, — брак и повод вернуть PR.
  Существующие asserts не ослаблены. Глю-код в omit — только с обоснованием.
- **Пороги покрытия — только вверх** (ratchet): понижение порога — блокер.
  Diff-cover: изменённые строки покрыты ≥85% (стики-комменты CI в PR).
- **Реестр хвостов**: каждая новая заглушка / отложенный кусок / «сделаем
  перед продом» — строка в `docs/registry.md` в этом же PR.
- **Секреты**: реальных секретов в диффе нет; фейковые в тестах выглядят
  фейково (`sk-test-…`, dummy, invalid) — иначе ночной gitleaks.
- **Границы**: модули сервера общаются через сервисные интерфейсы (не
  через чужие таблицы); скоуп — текущий этап продукта, фич из будущих
  этапов нет даже «заодно».

## Вердикты

- **Принято** → squash-мерж: после ревью взвести авто-мерж
  (`gh pr merge <PR> --squash --auto`) — вольётся по зелёному CI.
  Авто-мерж взводит только основная сессия и только после ревью.
- **Замечание** → комментарий **в тред PR** (вотчер агента его разбудит),
  НЕ в issue — написанное только в issue агент не увидит (проверено
  кровью: решение владельца пролежало в issue незамеченным, пока он сам
  не заметил простой). Замечание формулировать решаемо: что не так,
  варианты, критерий «после чего волью». Агент чинит и пушит без
  согласования — ждать его пуш, не чинить за него.
- **Обоснованное отклонение от спеки** агентом — легально: оценивать
  аргументы, не букву спеки. Принял отклонение — зафиксируй это в треде явно.
- **Конфликт с main** → чинит пришедший вторым у себя в worktree:
  коммент в тред «конфликт — разреши у себя: `git fetch && git merge
  origin/main`» (+ что с чем свести, если знаешь по соседнему PR);
  генерённые файлы не мержатся руками — перегенерируются.

## После мержа

- Доска: `tools/claude/board_status.sh <N> done` (`Closes #N` закрыл issue
  автоматически, но статус доски — за основной сессией).
- Уборка: свой worktree агент прибирает сам (его вотчер увидит MERGED);
  осиротевшие/автопилотные мастерские — уборщик
  `tools/claude/wt_janitor.py` (удаляет только механически доказанное
  «всё влито»). Основной чекаут — подтянуть main (`git pull`).
- Автопилот: мерж PR суб-агента освобождает слот — запустить следующую
  `auto`-задачу по приоритету (слоты вычисляются с доски: `auto` ∧
  In progress; правила выбора и непересечения — скилл `/duty`).
- PR менял процесс/инфру/пороги → соответствующий скилл (`/devops`,
  `/release`, `/spec`, `/review`) обновлён тем же PR —
  не обновлён, это было замечание, а теперь follow-up issue.
- Доклад владельцу — итогами («влито: #… — что дало»), без пошагового шума.

## Грабли

- **После каждого мержа остальные открытые PR становятся BEHIND** (ruleset
  требует актуальности ветки) — не чинить руками за агентов и не жать
  «Update branch»: вотчер бебиситинга будит владельца PR на отставание, он
  мержит origin/main сам. Взведённый авто-мерж после его пуша доедет сам.
- **Авто-мерж на Release PR — никогда**: Release PR мержится только по
  явному «релизь» от владельца, ритуал — скилл `/release`.
- **Draft PR не ревьюим** до перевода в ready — черновик означает, что
  агент ещё работает; событие вотчера по draft — просто ждать.
- Squash «сжигает» ветку PR — замечания после мержа в ту же ветку не
  отправлять, только новая issue / новый PR от свежего origin/main.
