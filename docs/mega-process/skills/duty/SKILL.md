# Дежурство основной сессии

**ЖИВОЙ документ**: изменились вотчеры/ритуалы/правила диспетчеризации →
обнови этот скилл ТЕМ ЖЕ PR. Основная сессия — та, что живёт в основном
чекауте (не в worktree).

## Обязанности (сводка)

Вотчеры очереди PR и issues · ревью и мерж (единственная, кто мержит;
чеклист — скилл `/review`) · статусы доски (spec/review/done) · спеки по
«распиши #N» (скилл `/spec`) · Release PR (скилл `/release`, только по
«релизь») · диспетчеризация автопилота · уборка worktree.

## Стартовый ритуал новой сессии

1. Взвести инструментом **Monitor (persistent: true)** ОБА вотчера:
   `bash tools/claude/pr_watcher.sh` (очередь PR) и
   `bash tools/claude/issue_watcher.sh` (issues/автопилот).
   НЕ через Bash run_in_background и НЕ через `&` — процесс мимо харнесса
   не разбудит сессию. Конструктивные решения задокументированы в самих
   скриптах — не переписывать по памяти.
2. Свериться с доской и очередью PR (`gh pr list`), проверить свободные
   слоты автопилота, догнать зависшее.
3. Утром — глянуть ночные прогоны (e2e, security).

Живость вотчеров страхует хук-гард (`tools/claude/watcher_guard.sh` в
`.claude/settings.local.json` основного чекаута): SessionStart впрыскивает
инструкцию, Stop блокирует завершение хода при мёртвом вотчере. Синглтон в
скриптах: новый экземпляр вытесняет старый (некролог exit 143 при
вытеснении — штатный).

## Обработка событий вотчера PR

- **Новый PR** → доска In review → ревью по скиллу `/review` → авто-мерж
  после ревью (`gh pr merge N --squash --auto`; на Release PR — никогда).
- **`behind: true`** → `gh pr update-branch N` (после каждого мержа
  остальные отстают — это штатный каскад; ruleset требует актуальности).
- **Красный CI / замечание** → коммент в ТРЕД PR (вотчер агента разбудит
  его сам; писать в issue бесполезно — агент его не перечитывает).
  Суб-агенту автопилота — SendMessage (контекст жив).
- **Мерж** → доска Done → `git fetch && git merge --ff-only origin/main` +
  удалить локальную ветку → уборка мастерских: `python3
  tools/claude/wt_janitor.py --yes` (удаляет только доказанное «чист +
  целиком во влитом PR»; запертые = живые не трогает; суб-агент не может
  удалить каталог, в котором стоит) → **проверить слот автопилота**.

## Автопилот: диспетчеризация (правила — CLAUDE.md «Автопилот рутины»)

- Слоты НЕ «помнятся», а вычисляются с доски: `auto` ∧ In progress; кап 2
  (поднимать до 3 только когда конвейер обкатан; качество держат два
  инварианта: мержи всё равно последовательны через основную сессию, а
  дополнительный слот заполняется ТОЛЬКО задачей без пересечения
  файлов/модулей с активными — иначе слот ждёт).
- Точки диспетчеризации: мерж PR автопилота (слот освободился → запустить
  следующего по приоритету p1>p2>p3) · событие issue-вотчера (новая
  рутина → триаж → спека по `/spec` → лейбл → запуск при свободном
  слоте) · старт сессии.
- Выбор следующей задачи: приоритет, затем непересечение — по спекам
  сверить зоны/файлы с активными слотами. Блокирует пересечение ЛОГИКИ
  (общий модуль/функция/общий список-реестр); чисто аддитивные соседства
  (новые независимые поля конфига, новые ключи локализации, новые строки
  реестра) НЕ блокируют: второй мержит `git merge origin/main`, конфликт
  тривиален. Слишком строгая трактовка держит слот пустым зря.
- Запуск: Agent tool, `isolation: "worktree"`, промпт-вертикаль по спеке →
  PR с Closes #N; агенту сказать НЕ бебисить (конвейер у основной сессии)
  и напомнить грабли голого worktree (нет gitignored-файлов — копировать
  из основного чекаута, не выдумывать).
- **Спящий суб-агент — пинг при тишине**: суб-агент, от которого долго нет
  ни PR, ни вопросов, мог остановиться на развилке и молча ждать —
  SendMessage «где ты?» вместо ожидания.
- Заблокированная задача → причина В ЗАГОЛОВКЕ issue (`[после X] …`) +
  коммент, доска — в свой бэклог: блокировка должна быть видна владельцу.
- **Два бэклога**: `backlog` = Продуктовый (идеи, продуктовые задачи, всё
  ждущее решения/участия владельца — в т.ч. платные запуски);
  `tech` = Технический (техдолг/инфра, едет автопилотом: лейбл auto или
  очевидная рутина). Триаж новой issue выбирает колонку сразу;
  сомнение = продуктовый (владелец увидит и решит).
- Развилка владельца у суб-агента → лейбл `needs:owner`, задача на паузе,
  вопрос владельцу в основной сессии.

## Владелец в петле и вкладка «Мои действия»

Владелец решает: запуск инстансов-эпиков, живые утверждения UI,
продуктовые развилки, «релизь», платные действия, сносы стендов/данных.
Всё, что ждёт лично его, — лейбл `needs:owner` (карточка попадает во
вкладку доски «Мои действия»; фильтр `label:"needs:owner" -status:Done`).
Владелец сделал свою часть, а задача живёт дальше → СНЯТЬ лейбл.

## Доклады

- Итогами, не по-чековыми статусами: «влито: …», «по автопилоту: …».
- Длинные кампании — пульсы с живыми числами (обычно каждый час).
- Запуск p1 по автопилоту — доклад сразу, не в дайджесте.
- Влит PR, меняющий CLAUDE.md → напомнить владельцу: активным агентам
  «git fetch && git merge origin/main + перечитай CLAUDE.md» (в worktree
  своя копия, без merge перечитают старую).
- Никаких условных инструкций владельцу («скажи X, когда Y») — инструкция
  выдаётся в момент, когда исполнима.
