# Спека задачи: шаблон и стандарты

**ЖИВОЙ документ**: изменились шаблон, лейблы или правила координации →
обнови этот скилл ТЕМ ЖЕ PR.

## Кто и когда

Спеку пишет основная сессия (или её суб-агент по этому скиллу): по команде
владельца «распиши #N», при триаже автопилота (`auto` без спеки) и при
создании issue, которую сразу можно отдать в работу. Готовая спека =
лейбл `spec:ready` + доска `tools/claude/board_status.sh N spec`.

## Шаблон (разделы обязательны, порядок фиксирован)

```
## Контекст
Почему задача существует: симптом/находка с ФАКТАМИ (числа, ссылки на
замеры/логи/issue). Что уже есть в кодовой базе по теме.

## Что сделать
Пронумерованные шаги с именами файлов/модулей. Технические решения,
которые УЖЕ приняты, — фиксировать (чтобы агент не перерешивал);
открытые — явно помечать «решить в PR, обосновать».

## Критерии приёмки
Каждый пункт ПРОВЕРЯЕМ командой/числом («не на веру»). Тесты утверждают
поведение; пороги покрытия и diff-cover держатся; для перф-задач —
замер до/после в теле PR.

## Границы
Что НЕ делать: чужие стенды/worktree, пороги, соседние домены, отложенное
(→ строка в docs/registry.md тем же PR). Для UI: новые элементы — только
через UI Lab (Lab-first, ≥5 вариантов, утверждение владельца вживую).

## Грабли
Проверенные кровью, релевантные ИМЕННО этой задаче — из скиллов
(/devops и т.д.), памяти проекта и связанных issues. Плюс
координация: какие параллельные PR/агенты трогают те же файлы и как
разруливать (обычно «пришедший вторым — git merge origin/main»).
Задача трогает персональные данные (новые поля/хранилища/потоки,
внешние сервисы, LLM-промпты, пуши) → в грабли — ссылка на чеклист
`/gdpr` и что именно из него релевантно.
```

## Стандарты качества

- **Privacy-верификация — обязательный финал КАЖДОЙ спеки** (если проект
  прошёл этап 10 плейбука): перед постановкой `spec:ready` прогнать спеку
  через чеклист `/gdpr` («новая фича → обязательства»). Итог — явная
  строка в конце спеки: `GDPR: не применимо (данных не трогает)` либо
  `GDPR: применимо — учтено в пунктах …`. Спека без этой строки
  `spec:ready` не получает.
- **Факты vs догадки**: всё дёшево проверяемое проверить командой ДО
  записи в спеку (grep по коду, `gh pr diff`, замер, доки). Догадку
  помечать догадкой.
- **Самодостаточность**: агент читает issue ОДИН раз при взятии — спека
  обязана содержать всё (включая грабли окружения: голый worktree без
  gitignored-файлов, нестандартные порты, свои изолированные ресурсы).
- **Смета**: у задач с платными ресурсами (стенды, машины) — оценка
  $/сутки и правило «сносить только по команде владельца».
- **Пульсы**: длинные кампании (>1 ч работы) — периодичность пульсов в
  issue прописать явно (обычно каждый час, живая таблица одним комментом).

## Лейблы при создании issue

- Пара команд обязательна: `gh issue create --label "..."` +
  `tools/claude/board_status.sh N backlog|tech|spec` (create НЕ добавляет
  на доску — карточку без второй команды владелец не увидит).
- Авторство: `by:claude-code` (основная сессия/суб-агент) или
  `by:agent-claude` (рабочий агент). Тип/домен/приоритет — всегда.
- **`auto`** — если рутина для автопилота: type:bug/debt, БЕЗ видимого UI,
  без продуктовых решений/платного/сносов. Сомнение = не вешать.
- **`needs:owner`** — если внутри есть развилка, требующая решения
  владельца (карточка попадает во вкладку «Мои действия»; сделал своё —
  сними лейбл).

## Анти-паттерны

Спека-эссе без проверяемых критериев · критерий «работает» без команды
проверки · отсутствие раздела «Границы» · грабли скопом вместо релевантных ·
скрытая зависимость от другой задачи без явного «blocked by #N» ·
отсутствие строки «GDPR: …» в конце спеки (после этапа 10).
