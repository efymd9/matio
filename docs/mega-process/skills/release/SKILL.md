# Релизный ритуал

**ЖИВОЙ документ**: изменились пороги, шаги ритуала или механика
release-please → обнови этот скилл ТЕМ ЖЕ PR.

## Железные правила

- Release PR мержит **только основная сессия** и **только по явному
  «релизь» от владельца**. Авто-мерж на Release PR не взводить никогда.
- Release PR (`release-please--branches--main--…`) аккумулирует changelog
  сам после каждого мержа в main — его не трогать руками, в его ветку не
  коммитить.
- Версия одна на весь продукт: тег `vX.Y.Z` + `version.txt` (+ бампы
  файлов версий сервера и приложения строками с аннотацией
  `x-release-please-version` — делает бот).

## Пре-релизный ритуал (по порядку; пункты со «*» — если модуль внедрён)

1. **E2E***: запустить e2e-прогон (`gh workflow run e2e-nightly` или
   локальный) → дождаться зелёного. Красный → чинить/issue, релиз стоп.
2. **QA-прокликивание**: чек-лист критических сценариев на свежей сборке +
   свободное исследование; вердикт без критических находок. Критическая →
   issue + фикс + повторный прогон.
3. **Перф-рэтчет*** (после этапа 09): зачётный нагрузочный прогон
   проходит пороги паспорта ёмкости. Стенд платный: поднимать по команде
   владельца. Ухудшение против эталона → issue, релиз обсуждается.
4. **Реестр хвостов**: `docs/registry.md` — сверить, нет ли пунктов
   «сделать перед продом», блокирующих именно этот релиз.

## Мерж и пост-релиз

1. По «релизь»: `gh pr merge <Release PR> --squash` (основная сессия).
2. Бот создаст тег + GitHub Release; проверить: `gh release list -L 1`.
3. Автодеплой staging на пуш в main: дождаться зелёного деплой-workflow,
   смоук: `curl https://<staging-домен>/healthz` — поле `version`
   совпадает с релизом.
4. Доска: закрытые релизом issues должны уехать в Done (обычно сами через
   Closes); пробежать `gh issue list --search "is:open"` на предмет
   зависших.
5. Если менялись пороги/паспорта — обновить эталонные issue и скиллы тем
   же днём.

## Грабли

- **Release PR создаётся от имени GitHub App, не GITHUB_TOKEN**: PR от
  GITHUB_TOKEN не триггерят workflow (ограничение GitHub) — CI на Release
  PR не запустится и ruleset его не пропустит. После переносов/пересозданий
  репо проверять установку App, иначе release-please молча падает по
  авторизации.
- Squash-мерж «сжигает» ветку Release PR — бот пересоздаст следующий сам.
- Релиз в пятницу вечером / перед сном — не делаем: пост-релизную сверку
  некому смотреть.
