# Этап 03 — CI и качество

## Что вы получите

Каждый PR автоматически проверяется: линт и тесты сервера и приложения,
покрытие с рэтчетом («порог только вверх»), diff-cover (изменённые строки
покрыты ≥85%), стики-комментарии с покрытием прямо в PR. Ночью — скан
уязвимостей зависимостей и утёкших секретов. Чеки становятся обязательными
в ruleset main — красное физически не вливается.

## Что делает человек

1. Ничего платного. Для приватного репо следите за квотой Actions
   (2000 мин/мес бесплатно; расход виден в Settings → Billing).
2. Решите стартовые пороги покрытия вместе с агентом — честные для
   текущего состояния кода (правило: порог = текущее покрытие, округлённое
   вниз; дальше он только растёт).
3. Скормите промпт. После зелёного первого прогона — добавьте чеки в
   ruleset (агент подскажет имена).

## Промпт для агента

```
Настрой CI и контроль качества по плейбуку docs/mega-process/ (этап 03).
Сначала выясни у меня стек сервера и приложения (языки, тест-раннеры,
менеджеры пакетов), если не очевидно из репо. Работай веткой + PR.

1. Workflow server-ci (.github/workflows/server-ci.yml), триггеры
   pull_request + push в main, с concurrency-группой (новый пуш в PR
   отменяет устаревший прогон; на main не отменяем):
   - checkout с fetch-depth: 0 (diff-cover сравнивает с origin/main);
   - сервисы данных (Postgres/Redis/…) — docker run в шаге (не services:),
     если тестам нужны нестандартные конфиги;
   - линт + формат-чек (наш линтер);
   - тесты с покрытием и порогом-рэтчетом в конфиге проекта
     (пример Python: fail_under в [tool.coverage.report] pyproject.toml);
   - diff-cover: изменённые строки PR покрыты ≥85%
     (diff-cover coverage.xml --compare-branch origin/main --fail-under 85);
   - стики-коммент с покрытием в PR
     (marocchino/sticky-pull-request-comment, permissions:
     pull-requests: write);
   - сборка docker-образа сервера (если серверу предстоит деплой
     контейнером — этап 05).
2. Workflow app-ci для приложения, та же структура: анализ/линт → тесты с
   покрытием → фильтр покрытия БЕЗ генерённого и стендового кода → порог →
   diff-cover → стики-коммент. Возьми за образец
   docs/mega-process/tools/qa/mobile_coverage.py (написан под Flutter/lcov;
   адаптируй список исключений под наш кодоген и положи в tools/qa/).
   Если у приложения есть нативные сборки (Android/iOS) — отдельные джобы,
   на PR запускай их только при изменении нативных файлов
   (dorny/paths-filter), на push в main — всегда (страховочная сетка).
3. Ночной security-workflow (.github/workflows/security.yml, schedule +
   workflow_dispatch): osv-scanner по локфайлам + gitleaks по ВСЕЙ истории
   (fetch-depth: 0). ГРАБЛЯ: gitleaks-action ниже v8.25 молча игнорирует
   [[allowlists]] с condition=AND из .gitleaks.toml — пинуй свежую версию.
   Это сигнал, не ворота PR: находки чинятся отдельными PR.
4. .github/dependabot.yml: экосистемы наших пакетных менеджеров +
   github-actions, интервал weekly.
5. Контрактный ритуал (если сервер и приложение общаются по API):
   установи docs/mega-process/tools/gen_api.sh в tools/gen_api.sh,
   адаптировав под наш стек (экспорт OpenAPI из кода сервера + генератор
   клиента приложения). В CI сервера добавь проверку актуальности
   контракта (экспортированная спека совпадает с закоммиченной). Правило
   в CLAUDE.md: изменил контракт → перегенерировал клиент ТЕМ ЖЕ PR;
   генерённое руками не правится и не мержится — только перегенерация.
6. CLAUDE.md — раздел «Тесты и покрытие»: ratchet (поднял покрытие —
   подними порог тем же PR; понижать нельзя); diff-cover ≥85; тест обязан
   утверждать поведение (asserts на результат/состояние/ошибку) — тест,
   исполняющий строки ради процента, брак; существующие asserts не
   ослаблять; нетестируемый глю-код — в omit с обоснованием, а не
   театральный тест; фейковые секреты в тестах обязаны выглядеть фейково
   (sk-test-…, dummy, invalid) — иначе их пометит ночной gitleaks.
7. Прогони всё локально до пуша; первый прогон CI покажи мне. После
   зелёного — добавь имена джоб в ruleset main как required status checks
   СО strict-политикой (ветка обязана быть актуальной перед мержем —
   именно она рождает штатный каскад «после каждого мержа остальные PR
   становятся BEHIND», который разруливают вотчеры) и обнови скилл
   /review (пороги).
```

## Критерии готовности

- [ ] PR с намеренно сломанным линтом/тестом краснеет; после фикса
      зеленеет без перезапуска руками.
- [ ] PR, понижающий порог покрытия, не проходит ревью (правило в
      CLAUDE.md и /review); PR с непокрытыми изменёнными строками валит
      diff-cover.
- [ ] В PR появляются стики-комментарии с покрытием (и обновляются, а не
      плодятся).
- [ ] `gh workflow run security` — оба джоба зелёные (или находки
      превращены в issues).
- [ ] Ruleset main требует джобы CI; PR с отставшей веткой требует
      Update branch → перегон CI.

## Бюджетные развилки

- **Эконом**: GitHub-раннеры. Публичное репо — бесплатно и безлимитно;
  приватное — следить за квотой (кэшируйте зависимости, гоняйте нативные
  сборки только по paths-filter — это и есть главная экономия минут).
- **Как у оригинала**: внешние раннеры (Depot, ~$20/мес план Developer) —
  сервер-CI ~2.5 мин, мобильные сборки ~2–4 мин, macOS на M-чипах. Триггер
  апгрейда: CI стабильно дольше ~10 минут ИЛИ очередь из PR агентов ждёт
  раннеров (при 2+ параллельных агентах это быстро становится узким
  местом). Замер оригинала: раннер вдвое «толще» НЕ дал ускорения на
  непараллелящихся фазах — берите размер под реальный профиль джобы, а не
  «побольше».
- E2E на эмуляторе (мобильное приложение + реальный бекенд) — дорогой и
  хрупкий ярус: оригинал держит его ночным smoke-прогоном + ручным
  запуском перед релизом, НЕ воротами PR. Подключайте, когда появится
  что терять; эмулятору нужен KVM — на внешних раннерах его может не быть.
