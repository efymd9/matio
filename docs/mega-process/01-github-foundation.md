# Этап 01 — GitHub-фундамент

## Что вы получите

Репозиторий, в котором процесс может жить: система лейблов для задач,
Projects-доска со статусами (единственное место, где видно состояние всех
работ), защита ветки main (в неё нельзя влить красное или устаревшее) и
каркас CLAUDE.md — конституция проекта, которую каждый агент читает при
старте.

## Что делает человек

1. Заведите аккаунт GitHub (если нет). Решите: **публичное репо** (всё
   бесплатно, включая rulesets и Actions) или **приватное** — тогда для
   rulesets/branch protection нужен GitHub Pro (~$4/мес), а минуты Actions
   ограничены бесплатной квотой (2000 мин/мес).
2. Установите инструменты: `git`, `gh` (GitHub CLI), `jq`,
   Claude Code (`npm install -g @anthropic-ai/claude-code` или нативный
   установщик с claude.com/claude-code).
3. Авторизуйте gh: `gh auth login` → выберите GitHub.com, HTTPS, логин
   через браузер. Затем добавьте скоуп для досок:
   `gh auth refresh -s project` (без него команды `gh project *` откажут).
   Проверка: `gh auth status` показывает scopes: `project, repo, workflow`.
4. Создайте репозиторий (пустой или с существующим кодом) и склонируйте
   его. Если код уже есть — убедитесь, что дефолтная ветка называется
   `main`.
5. Запустите Claude Code в корне репо и скормите промпт ниже.

## Промпт для агента

```
Настрой GitHub-фундамент процесса разработки по плейбуку docs/mega-process/
(этап 01). Репозиторий — текущий; owner и имя возьми из `gh repo view`.
Прежде чем менять что-либо на GitHub, покажи мне план одним сообщением.

1. Лейблы (gh label create, идемпотентно — существующие пропускай):
   - type:feature, type:bug, type:debt, type:idea
   - domain:backend, domain:app, domain:infra, domain:qa
   - p1, p2, p3 (p1 — «горит»)
   - spec:ready (спека готова, можно брать в работу)
   - auto (кандидат на автопилот — этап 08, завести сразу)
   - needs:owner (ждёт решения/действия владельца)
   - by:agent-claude, by:claude-code (авторство issue: рабочий агент /
     основная сессия; нужны, потому что все issue создаются одним
     gh-токеном владельца и по автору их не различить)
   Цвета выбери сам, осмысленно по группам.
2. Projects-доска (v2): `gh project create --owner <owner> --title "<repo>"`.
   Затем через GraphQL (gh api graphql, мутация updateProjectV2Field на
   поле Status) задай ровно шесть опций статуса:
   «Продуктовый бэклог», «Технический бэклог», «Spec ready», «In progress»,
   «In review», «Done».
   ВАЖНАЯ ГРАБЛЯ (проверено кровью у оригинала): любой updateProjectV2Field
   пересоздаёт ID ВСЕХ опций поля. Сейчас доска пуста и это безопасно, но
   запомни правило на будущее: смена набора колонок = снимок всей доски до,
   восстановление статусов после. Настраивай опции ОДНОЙ мутацией.
   После настройки получи и покажи мне: PROJECT_ID, FIELD_ID поля Status и
   ID всех шести опций (они понадобятся на этапе 02 для board_status.sh).
3. Ruleset для main (gh api repos/{owner}/{repo}/rulesets, POST):
   - требовать PR перед мержем (запрет прямых пушей в main),
   - required status checks пока НЕ задавать — CI появится на этапе 03;
     тогда же в ruleset добавятся чеки CI и strict-политика «ветка
     актуальна перед мержем» (в rulesets она живёт внутри правила
     required_status_checks и без чеков не существует).
   Если API откажет (приватное репо на Free-плане) — скажи мне, что нужен
   GitHub Pro, и продолжай без ruleset, оставив TODO-строку в docs/registry.md.
4. Каркас файлов в корне репо (создай PR обычным путём: ветка от
   origin/main, осмысленные коммиты):
   - CLAUDE.md с разделами (наполнение — короткое, по нашему проекту;
     спроси меня, что за продукт и какой стек, прежде чем писать):
     «Проект» (одним абзацем + структура монорепо), «Главные правила»
     (скоуп = текущий этап продукта, ничего из будущих «заодно»;
     контракты — источник правды; приватность: данные пользователей
     НИКОГДА не пишутся в логи/трекер ошибок/аналитику — только id,
     статусы, длительности; минимальный код без спекулятивных абстракций;
     правки хирургические; реестр хвостов docs/registry.md — любая
     заглушка/отложенное — строка в реестре тем же PR; процессные скиллы —
     ЖИВЫЕ документы: изменил процесс — обнови скилл тем же PR),
     «Команды» (линт/тесты/сборка нашего стека), «Трекер задач» (правила
     из этого этапа: задачи ТОЛЬКО в Issues; создал issue → сразу на
     доску; лейблы; спеки пишутся по команде «распиши #N»).
   - docs/registry.md — реестр хвостов: заголовок + правило + пустая
     таблица «Что | Блокирует | Когда закрывать».
   - docs/adr/README.md — формат ADR (контекст → решение → последствия,
     нумерация NNNN-slug.md) + пустой список.
5. Проверь итог командами и покажи мне: `gh label list`,
   `gh project list --owner <owner>`, ruleset через API, дерево docs/.
```

## Критерии готовности

- [ ] `gh label list` показывает все лейблы групп type/domain/priority +
      spec:ready, auto, needs:owner, by:*.
- [ ] Доска существует, поле Status имеет ровно 6 опций; PROJECT_ID,
      FIELD_ID и ID опций записаны (понадобятся на этапе 02).
- [ ] Прямой пуш в main отклоняется (изменения — только через PR).
      Требование актуальности ветки появится на этапе 03 вместе с чеками CI.
- [ ] В репо есть CLAUDE.md, docs/registry.md, docs/adr/README.md.
- [ ] Тестовая issue: `gh issue create --title test --label type:idea` —
      и вы видите, что на доске её НЕТ (это грабля, которую закрывает
      board_status.sh на этапе 02). Удалите тестовую issue после проверки.

## Бюджетные развилки

- **Эконом**: публичное репо — rulesets, Actions и Projects бесплатны.
  Если код приватный по сути — приватное репо без rulesets тоже работает:
  дисциплину «только PR, только зелёное» держит процесс (основная сессия
  просто не мержит мимо правил), но механической защиты нет.
- **Как у оригинала**: приватное репо в организации, план Team
  (~$4/юзер/мес), ruleset `protect-main` с обязательными чеками CI и
  актуальностью ветки. Апгрейд оправдан, как только агентов больше одного:
  механическая защита main дешевле одного случайно влитого красного PR.
