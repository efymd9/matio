# Мега-процесс: переносимый плейбук разработки с Claude Code

Это дистилляция реального процесса живого продукта (бекенд + мобильное
приложение), который несколько месяцев разрабатывается связкой
«один человек-владелец + агенты Claude Code» — с CI, деплоем, бэкапами,
нагрузочными кампаниями и автопилотом рутины. Всё, что здесь написано,
проверено на практике; грабли описаны честно, потому что они — главная
ценность передачи.

## Как этим пользоваться

**Быстрый старт**: скопируйте каталог в свой репозиторий и вставьте в
Claude Code единственный промпт из [`START.md`](START.md) — агент сам
прочитает плейбук, заведёт внедрение задачами в вашем же трекере и
поведёт вас по этапам 01–05, объясняя каждый шаг. Ручной маршрут — ниже.

1. Скопируйте каталог `mega-process/` целиком в свой репозиторий
   (например, в `docs/mega-process/`) — промпты этапов ссылаются на его
   файлы (`skills/`, `tools/`).
2. Идите по этапам по порядку. В каждом этапе:
   - раздел **«Что делает человек»** — выполняете сами (регистрации,
     токены, оплаты, клики в UI вендоров);
   - раздел **«Промпт для агента»** — копируете целиком в свой Claude Code
     в корне репозитория. Промпты самодостаточны: агент сам спросит у вас
     недостающие креды и решения, когда до них дойдёт;
   - раздел **«Критерии готовности»** — проверяете, что этап действительно
     завершён, прежде чем идти дальше.
3. Этапы 01–07 — ядро, проходить по порядку. Этапы 08–10 — модули
   зрелости: подключайте, когда появится потребность.

Плейсхолдеры в файлах: `{{OWNER}}` — ваш GitHub-логин/организация,
`{{REPO}}` — имя репозитория, `{{PROJECT}}` — название продукта,
`{{MAIN_CHECKOUT}}` — абсолютный путь основного чекаута, `{{ДАТА}}` —
дата снимка в шаблонах карт. Агент подставляет их при установке — это
прописано в промптах; параметры Projects-доски (owner, номер, ID поля и
опций) живут в `tools/claude/board.env` (создаётся на этапе 02).

## Почему это работает: четыре кита

1. **Замкнутый PR-цикл.** Владелец не передаёт сообщения между агентами и
   не бегает за ними. Команда «Делай #N» самодостаточна: агент читает
   спеку из issue, делает вертикаль, открывает PR — и **бебиситит его до
   мержа** (вотчер будит агента на красный CI, комментарий ревью, конфликт;
   хук физически не даёт «сделать PR и уйти»). Ревьюер общается с агентом
   только через тред PR. Единственная точка мержа — основная сессия.
2. **Доска — единый источник правды.** Задачи живут ТОЛЬКО в GitHub
   Issues, статусы — ТОЛЬКО на Projects-доске. Ни чатов, ни блокнотов, ни
   «помню, что обещал». Владелец открывает доску и видит всё: что в
   работе, что ждёт его лично (вкладка «Мои действия»), что готово.
3. **Живые документы-скиллы.** Процессные знания (как ревьюить, как
   релизить, карта инфраструктуры, грабли) лежат в репо как скиллы
   Claude Code с железным правилом: **изменил процесс/инфру/пороги —
   обнови скилл ТЕМ ЖЕ PR**. Устаревшая карта хуже её отсутствия.
4. **Лестница зрелости.** Процесс внедряется этапами, каждый даёт
   работающую систему: можно остановиться после 05 (CI + UI Lab + деплой)
   и жить прекрасно; автопилот (08) подключается, когда рутина реально
   заедает.

## Карта ролей

| Роль | Кто | Что делает |
|---|---|---|
| **Владелец** | человек | продуктовые решения, живые утверждения UI, платные действия, «релизь», раздача задач; НЕ передаёт сообщения между агентами |
| **Основная сессия** | Claude Code в основном чекауте | единственная мержит; ведёт доску; пишет спеки; ревьюит; диспетчеризует автопилот; держит вотчеры очереди PR и issues (скилл `duty`) |
| **Рабочие агенты** | Claude Code в git-worktree | берут issue со спекой, делают вертикаль (сервер+контракт+клиент одним PR), бебиситят свой PR до MERGED, прибираются |
| **Автопилот** | суб-агенты основной сессии | рутина с лейблом `auto` (баги/техдолг без UI и продуктовых решений) — этап 08 |

## Принцип «эконом-дефолт → апгрейд-врезки»

Каждый этап описывает самый дешёвый работающий вариант. Там, где оригинал
живёт дороже (выделенные CPU, managed Postgres, внешние CI-раннеры),
стоит врезка **«Как у оригинала»**: что именно куплено, почему (с числами)
и по какому триггеру апгрейд оправдан. Не покупайте вперёд: половина
апгрейдов оригинала случилась после конкретной боли, и это правильный
порядок.

## Этапы и что работает после каждого

Порядок не случаен: главная ценность процесса раскрывается на этапах
01–05, и UI Lab — часть этого ядра. Стенд компонентов и дисциплина
Lab-first должны появиться ДО деплоя: тогда уже к пятому этапу процесс
начинает работать по-настоящему — агенты гонят вертикали через PR-цикл,
CI держит качество, UI утверждается вживую, а мержи сами едут на staging.

## Три правила, которые нельзя выбрасывать

Если урезаете процесс под себя — эти три вещи оставьте, на них он стоит:

1. **Тело PR — единственный канал агента к ревьюеру, тред PR —
   единственный обратный канал к агенту.** Написанное только в issue
   агент не увидит (проверено кровью: решение владельца пролежало в issue
   незамеченным, пока работа стояла).
2. **Создал issue → сразу на доску** (`gh issue create` НЕ добавляет в
   Project) — иначе владелец задачу никогда не увидит.
3. **Живость документов**: скилл/карта, не обновлённые тем же PR, что
   изменил реальность, — начало гниения всего процесса.
