# Этап 06 — Данные: миграции и бэкапы, которые восстанавливаются

## Что вы получите

Дисциплину миграций expand-contract (никакой DDL не ломает предыдущую
версию кода) и настоящие бэкапы: ежедневный шифрованный дамп БД в
Cloudflare R2 + **ежемесячная автоматическая проба восстановления** —
единственное, что отличает бэкап от лотереи. Провал любого из джобов сам
заводит p1-issue в трекер.

## Что делает человек

1. Заведите аккаунт Cloudflare (бесплатный план). В дашборде включите R2
   (потребует карту, но бесплатной квоты — 10 ГБ — дампам маленького
   проекта хватит надолго).
2. Создайте R2 API-токен: R2 → Manage R2 API Tokens → Create — права
   Object Read & Write (можно сузить до будущего бакета после его
   создания). Получите Access Key ID / Secret Access Key и S3-эндпоинт
   вида `https://<account_id>.r2.cloudflarestorage.com`.
3. Положите секреты и переменные в репо (значения — из п. 2):
   ```
   gh secret set R2_ACCESS_KEY_ID
   gh secret set R2_SECRET_ACCESS_KEY
   gh variable set R2_BUCKET --body "<project>-db-backups"
   gh variable set R2_ENDPOINT --body "https://<account_id>.r2.cloudflarestorage.com"
   ```
4. Секрет доступа к БД: `gh secret set BACKUP_DATABASE_URL` (DSN staging-БД;
   агент подскажет точное значение) и `gh secret set FLY_BACKUP_TOKEN`
   (fly-токен для прокси к БД; та же грабля stderr, что на этапе 05).
5. age-ключ сгенерирует агент; вы сохраните приватный ключ в менеджер
   паролей И в `gh secret set BACKUP_AGE_SECRET_KEY` — без него дампы
   не расшифровать никогда.
6. Скормите промпт.

## Промпт для агента

```
Настрой дисциплину данных и бэкапы по плейбуку docs/mega-process/
(этап 06). Скрипты бери из docs/mega-process/tools/backup/ — копируй в
infra/backup/ ЦЕЛИКОМ, с комментариями (в них — оплаченные кровью
решения). Работай веткой + PR.

1. CLAUDE.md — раздел «Миграции»: только expand-contract — никаких DDL,
   ломающих предыдущую версию кода, в одном релизе с этим кодом (сначала
   expand-релиз: новое поле nullable/с дефолтом, код пишет в оба; потом
   contract-релиз: снос старого). Индексы на потенциально больших
   таблицах: обычный CREATE INDEX держит блокировку записи на всё время
   построения — трейд-офф с CONCURRENTLY фиксировать комментарием в
   миграции. Плюс правило идемпотентности мутаций: клиентские
   повторы не должны плодить дубли (client-generated id для сообщений,
   Idempotency-Key для остального — подстрой под нашу предметку).
2. Скрипты: infra/backup/backup_db.sh, restore_check.sh, setup_r2.sh из
   комплекта. В restore_check.sh проверь smoke-запросы под наш инструмент
   миграций (шаблон рассчитан на Alembic/alembic_version — замени, если у
   нас другой) и под нашу «главную» таблицу вместо users.
3. Сгенерируй age-ключ (age-keygen), отдай мне приватный ключ В ЧАТЕ ОДИН
   РАЗ (я сохраню в менеджер паролей и в секрет BACKUP_AGE_SECRET_KEY),
   публичный положи: gh variable set BACKUP_AGE_PUBLIC_KEY --body "age1…".
   В файлы репо ключи не писать.
4. Workflows (по образцу оригинала, объяснения — в комментариях;
   env-контракт каждого скрипта — в его шапке: секреты R2_ACCESS_KEY_ID /
   R2_SECRET_ACCESS_KEY маппятся в env AWS_ACCESS_KEY_ID /
   AWS_SECRET_ACCESS_KEY, остальные имена 1:1):
   - db-backup.yml: ежедневный cron + workflow_dispatch; guard-шаг — если
     секреты пусты, notice с ИМЕНАМИ пустых переменных (не значениями!)
     и мягкий пропуск: молчаливый пропуск без имени виновника уже стоил
     оригиналу четырёх холостых прогонов; установка клиентов Postgres
     ТОГО ЖЕ МАЖОРА, что сервер БД. ГРАБЛЯ: Debian-обёртка /usr/bin/pg_dump
     выбирает системную версию — пиновать реальные бинарники
     (echo "/usr/lib/postgresql/<N>/bin" >> $GITHUB_PATH) и печатать
     pg_dump --version в прогоне; прокси к БД (flyctl proxy к
     staging-Postgres); запуск infra/backup/backup_db.sh; при провале
     планового прогона — gh issue create с p1 (если открытой ещё нет —
     иначе комментарий в существующую).
   - db-restore-check.yml: ежемесячный cron + dispatch; services:
     vanilla-postgres того же мажора; тот же guard; запуск
     restore_check.sh (он сам проверяет свежесть дампа — мёртвый db-backup
     провалит и пробу); та же issue-эскалация при провале.
   - backup-setup.yml: только workflow_dispatch, одноразовый прогон
     setup_r2.sh (бакет + lifecycle retention 35 дней).
5. Прогон: запусти backup-setup, затем db-backup и db-restore-check
   вручную (gh workflow run + gh run watch), покажи мне зелёные прогоны и
   строку «OK: restore-проба пройдена…».
6. Ранбук docs/runbooks/db-restore.md: как восстановиться руками из
   последнего дампа (шаги с командами), включая шаг «restore после
   GDPR-удаления → повторный прогон удаления». Обнови /devops (раздел
   «Бэкапы») и docs/registry.md тем же PR.
```

## Критерии готовности

- [ ] `gh workflow run db-backup` → зелёный; в бакете появился
      `staging/db-<дата>.dump.age`.
- [ ] `gh workflow run db-restore-check` → зелёный, в логе «OK:
      restore-проба пройдена (миграции …, таблиц N)».
- [ ] Приватный age-ключ лежит в менеджере паролей владельца И в секрете
      репо; в git-истории его нет.
- [ ] Выключите секрет (переименуйте) → плановый прогон создаёт
      p1-issue. Верните секрет обратно.
- [ ] В CLAUDE.md — правила expand-contract и идемпотентности; /review
      проверяет миграции.

## Бюджетные развилки

- **Эконом**: unmanaged Postgres на Fly (1 нода, ~$2–4/мес) + эти бэкапы.
  Честная оценка: это «restore за вчера», RPO до 24 ч. Для проекта без
  живых пользователей — достаточно.
- **Как у оригинала**: Fly Managed Postgres (~$38+/мес) — PITR ~10 дней,
  HA, обслуживание. Триггер: живые пользователи, чьи данные больно терять
  даже за день, или первые деньги. Грабли managed-планов, оплаченные
  оригиналом: подключение приложения — только по прямому хостнейму
  (встроенный pgbouncer с transaction-пулингом ломает prepared statements
  asyncpg — запись деградировала в 54 раза); max_connections
  документация не сообщает — измерить самим и посчитать бюджет пула:
  (pool+overflow) × процессы + воркеры + служебные ≤ max_connections с
  запасом ≥25%; системные представления БД под пользователем приложения
  частично слепы (мониторинг строить на датчиках в приложении).
- Ежедневность/ретеншен: cron раз в день + retention 35 дней — дешёвый
  дефолт; больнее терять — чаще дампы, дольше retention (R2 копейки).
