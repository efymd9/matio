# Ранбук: запросы субъектов данных (GDPR ст. 15 / 17 / 20)

Читается, когда на `contact@matio.tv` пришло «выдайте мои данные» или
«удалите меня». Здесь только шаги и команды; правовая рамка, карта данных и
список процессоров — в скилле `/gdpr` (`.claude/skills/gdpr/SKILL.md`,
`references/data-map.md`, `references/processors.md`). Решения «отказать»,
«продлить срок», «это не наш субъект» принимает владелец (с юристом) — ранбук
их не автоматизирует.

## Сначала определи тип запроса

| Просят | Право | Куда |
|---|---|---|
| «Какие данные у вас обо мне», «пришлите копию» | доступ, ст. 15 | §3 «Экспорт» |
| «Отдайте в машиночитаемом виде», «перенесите» | портируемость, ст. 20 | §3 «Экспорт» (тот же файл; derived-поля помечаются в письме) |
| «Удалите аккаунт / меня» | стирание, ст. 17 | §4 «Стирание» |
| исправить, ограничить, возразить (ст. 16, 18, 21) | — | владелец + юрист; этот ранбук их не покрывает |

Срок — **30 дней с получения** (ст. 12(3)), бесплатно (ст. 12(5)). Продлить
ещё до двух месяцев можно только для сложных/массовых запросов, уведомив
субъекта в первый месяц — решение владельца. Часы тикают с момента
получения письма, не с момента верификации.

## 1. Приём

1. В день получения — строка в реестре (§6): номер `DSR-<год>-<NNN>`, дата,
   тип, хеш адреса, статус `received`. Имён и адресов в реестре нет: он
   лежит в репозитории. Хеш адреса (чтобы узнать повторный запрос того же
   человека, не храня адрес):

   ```bash
   printf '%s' 'address@example.com' | tr 'A-Z' 'a-z' | shasum -a 256 | cut -c1-8
   ```

2. Ответить субъекту, что запрос получен и срок — 30 дней. Ничего о данных в
   этом письме ещё нет.

## 2. Верификация личности — без документов

Удостоверение личности не запрашиваем: адрес аккаунта и есть учётная запись
(вход в Clerk — по коду на email). Достаточно двух проверок:

1. **Запрос пришёл с адреса аккаунта.** Clerk Dashboard → Users → поиск по
   адресу. Найден — запомнить `user_…` (он понадобится в §3). Не найден —
   либо у человека нет аккаунта (см. «Адрес без аккаунта» ниже), либо он
   пишет с другого адреса: попросить написать с адреса аккаунта, на чужой
   адрес ничего не отправлять.
2. **Человек контролирует этот адрес прямо сейчас.** Попросить войти на
   matio.tv (вход — код на email через Clerk) и сообщить, когда вошёл;
   сверить «Last signed in» на карточке пользователя в Clerk Dashboard.
   Совпало — верифицирован; статус в реестре → `verified`.

**Адрес без аккаунта.** Если адреса нет в Clerk, единственное, что о нём может
быть у нас, — строки `show_reminders` (форма «напомнить о новой серии» работает
без входа). Скрипт §3 ключуется по Clerk id и такой случай не покрывает:
ответ собирается руками — `select count(*) from show_reminders where email =
…` (только счётчик в чат/консоль, не строки), затем сами строки в файл
ответа; верификация — попросить ответить на письмо, отправленное на этот
адрес. Отписка (`/unsubscribe`) удаляет все строки адреса и часто закрывает
такой запрос целиком.

## 3. Экспорт (ст. 15 / 20)

### Что понадобится

- чекаут репозитория с `pnpm install`;
- `DATABASE_URL` **production** (пулер Neon — то же значение, что в
  `.env.local`, но скрипт файл не читает: значение передаётся в команде явно,
  выгрузка живого аккаунта — осознанное действие);
- по желанию, для вендорских половин: `CLERK_SECRET_KEY` (`sk_live_…`),
  `STRIPE_SECRET_KEY` (`sk_live_…`), `POSTHOG_PERSONAL_API_KEY` +
  `POSTHOG_PROJECT_ID` (проект `190233`). Значения — из менеджера паролей
  владельца или Vercel → Project → Settings → Environment Variables
  (Production). Ни одно из них не писать в файл и не печатать.

### Шаг 1 — выгрузка

```bash
DATABASE_URL='postgres://…' \
CLERK_SECRET_KEY='sk_live_…' STRIPE_SECRET_KEY='sk_live_…' \
POSTHOG_PERSONAL_API_KEY='phx_…' POSTHOG_PROJECT_ID=190233 \
pnpm export-user-data user_… --out ~/dsr/DSR-2026-001.json
```

`user_…` — Clerk id из §2. Без `--out` файл ляжет во **временный каталог
ОС** (`os.tmpdir()`, полный путь печатается последней строкой) как
`export-<userId>-<дата>.json` — никогда в текущий каталог, то есть в
репозиторий; `.gitignore` дополнительно закрывает `export-*.json` на случай
`--out` внутрь дерева. Файл создаётся с правами `0600` — это данные
человека, он не должен попасть в репозиторий, в issue, в чат агента.

Вендорские вызовы ограничены по времени (Clerk 15 с, Stripe 30 с на запрос,
PostHog 30 с на выражение): зависший вендор даёт `failed (TimeoutError)` в
`notes`, а не зависший терминал — половина из базы всё равно записывается.

В консоль скрипт печатает **только счётчики и статусы** — никаких значений:

```
subject: user_…
database rows: users=1 subscriptions=0 watch_progress=12 watch_days=5 trial_sessions=2 visitors=1 visitor_days=4 show_reminders=1
processors: clerk=received stripe=received (invoices=3) posthog=received (events=143)
notes (1):
  - clerk: the profile above is what the Backend API exposes; sign-in sessions and devices are not part of it — …
written ~/dsr/DSR-2026-001.json (mode 0600) — delete it once the reply has gone out
```

Что внутри файла: `database` — восемь таблиц, привязанных к человеку
(`users`, `subscriptions`, `watch_progress`, `watch_days`, `trial_sessions`,
`visitors` + `visitor_days`, `show_reminders` — по `user_id` **и** по адресу),
всегда все восемь ключей, даже с нулём строк; `processors.{clerk,stripe,
posthog}` — профиль Clerk, Customer + инвойсы Stripe, персона + события
PostHog; `notes` — что пропущено и почему. `stripe_events` (сырые вебхуки) и
`watch_segments` (агрегат без ключа пользователя) в выгрузку не входят.

Коды выхода: `2` — нет аргумента или `DATABASE_URL` (ничего не сделано);
`1` — упала база или запись файла; `0` — файл записан, даже если какой-то
вендор `skipped` (best-effort — вендорская половина не блокирует ответ).

### Шаг 2 — вендоры, которых скрипт не достал

`skipped` или `failed` в строке `processors:` → выгрузить руками и вложить
в ответ рядом с JSON:

| Процессор | Где | Что взять |
|---|---|---|
| Clerk | https://dashboard.clerk.com → Users → поиск по адресу → карточка | id, адреса (и верифицированы ли), имя, created, last sign-in. Сессии/устройства в экспорт не входят — субъект видит их сам в настройках аккаунта |
| Stripe | https://dashboard.stripe.com/customers → клиент (`cus_…` из `users.stripe_customer_id`) | карточка Customer (email, имя, billing address, created) и список инвойсов — «Export» на странице клиента. Инвойсы субъект и сам скачивает через Customer Portal |
| PostHog | https://eu.posthog.com/project/190233/persons → поиск `user_…` (distinct_id) | свойства персоны + вкладка Events → Export (CSV). Session replay в выгрузку не входит — это запись интерфейса с маской, не «данные о субъекте» в смысле ст. 15; при явном запросе — решение владельца |

Остальные процессоры (Meta, Google, OpenAI, Mux, Resend, Sentry, Vercel)
per-user выгрузки не отдают: у них хешированный email, клиентские id событий
или инфраструктурные логи с ретеншеном (`references/processors.md`). В письме
они перечисляются как получатели, без вложений.

### Шаг 3 — прочитать файл перед отправкой

Выгрузка идёт как есть, но два места могут нести **чужие** данные (ст. 15(4)):

- `visitors.referrer` — сырой `document.referrer` первого визита, может
  содержать чужие query-параметры; если содержит — обрезать до хоста;
- `show_reminders` — строки по адресу; если `user_id` в такой строке указывает
  на **другой** аккаунт (coalesce-backfill), убрать `user_id` из строки.

`ip_hash`, `stripe_customer_id`, `session_token`, `aid` остаются — это
данные субъекта, не секреты.

### Шаг 4 — ответ

Вложение: JSON (+ вендорские выгрузки), в зашифрованном архиве — пароль
отдельным сообщением/каналом:

```bash
age -p -o DSR-2026-001.json.age ~/dsr/DSR-2026-001.json   # спросит парольную фразу
```

Сопроводительное письмо (ст. 15(1), на языке аккаунта — es/en):

1. **цели обработки** — аккаунт и воспроизведение, история и позиция
   просмотра, биллинг (договор); первичная аудитория и антиабьюз (законный
   интерес); маркетинговая аналитика и письма-напоминания (согласие);
2. **категории данных** — то, что в файле, по разделам;
3. **получатели** — процессоры из `references/processors.md` (Neon, Vercel,
   Clerk, Stripe, Mux, Resend, PostHog; при согласии — Meta, Google, OpenAI;
   Sentry);
4. **сроки хранения** — по карте данных (`references/data-map.md` §2);
5. **права** — исправление, стирание, ограничение, возражение, отзыв
   согласия, жалоба в ICO / AEPD;
6. **источник** — сам субъект; страна — из IP запроса;
7. автоматизированных решений (ст. 22) нет.

Для ст. 20 — тот же JSON и есть машиночитаемый формат; в письме пометить,
что derived-поля (`country`, `attribution_*`, `converted`, флаги
`visitor_days`) приложены по ст. 15 и под ст. 20 не подпадают.

### Шаг 5 — хвосты

- удалить локальный файл и архив (`rm -P` на macOS / `shred` на Linux);
- реестр (§6): статус → `answered`, дата ответа.

## 4. Стирание (ст. 17)

### Приём и верификация

Как для доступа: строка в реестре (§6) в день получения, ответ «получили,
срок 30 дней», верификация по §2 — запрос с адреса аккаунта + вход на
matio.tv. Для стирания это важнее, чем для доступа: стёртое не вернуть, а
восстановление из бэкапа (§7 `db-restore.md`) — инцидент, не сервис.
Найденный в Clerk `user_…` — **записать сразу**: после удаления аккаунта
Clerk его уже не покажет, а скрипт и реестр ключуются по нему.

### Два пути — одна механика

Триггер — удаление аккаунта в Clerk; механика — `lib/erase-user.ts:eraseUser`,
которую запускают вебхук и скрипт с одним и тем же кодом:

| Путь | Когда | Что происходит |
|---|---|---|
| **Пользователь сам**: UserProfile → «Delete account» | человек может удалить сам — предложить это первым | Clerk шлёт `user.deleted` → вебхук → всё ниже автоматически |
| **Оператор**: Clerk Dashboard → Users → карточка → Delete user | верифицированный запрос, человек просит сделать за него | тот же вебхук, то же самое |
| **`pnpm erase-user <user_…> --apply`** | вебхук не дошёл (Clerk → Webhooks → endpoint → Messages: нет `200` по этому событию) или восстановление из бэкапа вернуло строки (§7 `db-restore.md`) | тот же код руками; идемпотентно — повтор локально ничего не меняет |

Что делает `eraseUser`, по порядку (тесты `app/api/webhooks/clerk/route.test.ts`
и `lib/erase-user.test.ts` пришпиливают порядок):

1. живая подписка Stripe → `cancel_at_period_end: true` (best-effort: сбой
   Stripe стирание не останавливает, но уходит в лог и Sentry по id — тогда
   отменить руками в Stripe Dashboard);
2. `stripe_customer_id` → тумбстоун `erased_customers` (иначе поздний вебхук
   Stripe воскресил бы аккаунт через `claimGuestCheckout`);
3. `DELETE FROM show_reminders` по адресу аккаунта и по `user_id`;
4. `DELETE FROM users` → каскады FK: `subscriptions`, `watch_progress`,
   `watch_days` удаляются; `trial_sessions`, `visitors`,
   `marketing_links.created_by` остаются с `user_id = NULL` (псевдонимно);
5. PostHog: person с `distinct_id` = Clerk id и его события —
   `DELETE …/persons/{id}/?delete_events=true` (best-effort, 5 с, без
   ретраев; сами события PostHog удаляет отложенной задачей, раз в неделю).
   Этот шаг идёт и когда строки `users` уже нет — так повтор скрипта
   добирает PostHog после сбоя.

### Скрипт

```bash
DATABASE_URL='postgres://…' pnpm erase-user user_…            # dry-run: только счётчики
DATABASE_URL='postgres://…' \
STRIPE_SECRET_KEY='sk_live_…' \
POSTHOG_PERSONAL_API_KEY='phx_…' POSTHOG_PROJECT_ID=190233 \
pnpm erase-user user_… --apply
```

`.env.local` скрипт не читает (там прод-креды) — каждая переменная явно;
без `DATABASE_URL` — exit 2, ничего не сделано. Без `--apply` — **dry-run**:
печатает, сколько строк было бы удалено и деидентифицировано, есть ли Stripe
customer / тумбстоун / живая подписка, сколько персон PostHog найдено по id
(заодно видно, читает ли ключ персон вообще) — и ничего не пишет. Вендорские
переменные опциональны: без `STRIPE_SECRET_KEY` живая подписка не отменится
(скрипт скажет `cancel by hand`), без ключа PostHog —
`posthog: skipped_unconfigured`. В stdout — только id, счётчики и статусы:

```
DRY RUN — erase user_…
subject: user_…
would delete: users=1 show_reminders=1 subscriptions=0 watch_progress=12 watch_days=5
would de-identify (user_id → NULL): trial_sessions=2 visitors=1 marketing_links=0
stripe: customer=none live_subscription=no
posthog: found persons=1
nothing changed (dry run — re-run with --apply)
```

Коды выхода: `2` — аргументы или нет `DATABASE_URL`; `1` — упала база
(повторить — стирание сходится); `3` — локально стёрто, но вендорский шаг
остался на операторе (строки `left for the operator` выше); `0` — всё.

Условие: аккаунт в Clerk уже удалён — скрипт Clerk не трогает. Если аккаунт
ещё жив, сначала удалить его в Dashboard: вебхук сделает всё сам, скрипт
тогда не нужен.

### PostHog руками — при `skipped_forbidden` или `failed`

`skipped_forbidden` (401/403): у personal key нет scope `person:write`
(ключ для HogQL-панелей админки создавался с `query:read`). Либо владелец
добавляет scope (PostHog → Settings → Personal API keys) и
`pnpm erase-user <id> --apply` повторяется (локально — no-op, PostHog —
заново), либо руками: https://eu.posthog.com/project/190233/persons → поиск
по `user_…` → карточка персоны → **Delete person** → галка «Delete all
events of this person» → подтвердить. `failed` (таймаут / 5xx) — повторить
скрипт позже или так же руками. Сигнал без запроса: строка
`erase user: PostHog person NOT erased` в логах Vercel и событие в Sentry по
`userId` — значит, этот шаг нужен.

### Что остаётся у процессоров — и почему

| Процессор | Что остаётся | Основание |
|---|---|---|
| Stripe | Customer (email, billing address) и инвойсы; подписка гаснет на конец периода, id клиента — тумбстоун. `customers.del` — решение владельца (`docs/registry.md`, `needs:owner`) | инвойсы — налоговые записи, ст. 17(3)(b); Customer — до решения владельца, в ответе пользователю так и написать |
| Resend | логи доставки (адрес, тема) | политика Resend: 30 дней, истекают сами |
| Бэкапы | зашифрованные дампы до 35 дней | ICO «put beyond use»: live-системы чистятся сразу, дампы истекают; restore → повторное стирание по реестру (§7 `db-restore.md`) |
| Meta / Google / OpenAI | хешированный email, id событий | per-user удаления нет; согласие отзывается на устройстве (`/cookies`) |
| Sentry / Vercel | `user.id` в событиях, runtime-логи | ретеншен плана (Sentry 90 дней, Vercel ≤ 1 сутки) |
| Clerk | ничего — источник истины, аккаунт удалён | — |

### Ответ и реестр

Ответить в 30 дней: что стёрто (аккаунт, история и позиция просмотра,
напоминания, аналитика), что и почему остаётся (таблица выше), срок жизни
бэкапов. Реестр (§6): статус `erased`, дата исполнения — по этой строке §7
`db-restore.md` повторяет стирание после восстановления из дампа старше
этой даты. Локально ничего не хранить.

## 6. Реестр заявок

Одна строка на запрос, без имён и адресов. Статусы: `received` → `verified`
→ `answered` / `refused` (с причиной в issue владельца) / `erased` (для ст. 17).

| № | Получен | Тип | Хеш адреса | Статус | Отвечен |
|---|---|---|---|---|---|
| — | — | — | — | — | — |
